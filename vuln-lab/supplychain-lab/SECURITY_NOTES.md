## 一、金鑰管理：本專案目前的問題

### 現況（⚠ 不安全，僅供教學）

`rsa_sign.py keygen` 會把私鑰以**明文 JSON** 寫入：

```
vuln-lab/supplychain-lab/keys/
├── ca_private.json          ← 根 CA 私鑰（明文）
├── ca_public.json
├── publisher_private.json   ← 發佈者私鑰（明文）
├── publisher_public.json
└── publisher_cert.json
```

**這在真實專案中是嚴重問題**——私鑰外洩 = 攻擊者可偽造任意簽章，
整條信任鏈瞬間失效。

### 已做的補救

1. **`.gitignore` 已排除私鑰**（兩層：專案根目錄 + 靶場目錄）
   ```
   vuln-lab/supplychain-lab/keys/
   **/*private*.json
   **/*.pem
   **/*.key
   ```

2. **CI workflow 已註記**正確做法：
   ```yaml
   # ★ 真實 CI 中，「私鑰」必須來自 secrets，絕不可進版控
   #   - name: Sign with Cosign (production)
   #     run: cosign sign-blob --key env://COSIGN_KEY sbom.json
   ```

## 二、生產環境的金鑰管理對照表

| 面向 | 本專案（教學） | 生產環境應做 |
|---|---|---|
| **私鑰儲存** | 明文 JSON 檔案 | HSM / KMS / Vault；或至少作業系統金鑰庫 |
| **私鑰權限** | 檔案權限（Windows 上無法精確控制） | 嚴格檔案權限（0600）+ 專用服務帳號 |
| **版控** | 已用 `.gitignore` 排除 | pre-commit hook 掃描；CI 檢查 |
| **金鑰輪替** | ❌ 無 | 定期輪替 + 舊金鑰撤銷 |
| **撤銷機制** | ❌ 無 | CRL / OCSP / 短效憑證 |
| **憑證到期** | ❌ 無（永久有效） | 明確 not_after + 自動續期 |
| **簽章演算法** | RSA-2048 | **Ed25519** 或 ECDSA（更快、更小、更安全） |
| **簽章工具** | 自製（標準庫） | Sigstore/cosign、OpenSSL、libsodium |
| **透明度** | ❌ 無 | Sigstore Rekor（公開可稽核的簽章日誌） |
| **審計** | ❌ 無 | 每次簽章記錄誰、何時、簽了什麼 |

### 為什麼推薦 Sigstore/cosign

本專案自己實作 RSA 是為了**理解機制**，但生產環境不該自己寫密碼學。

Sigstore 生態系解決了本專案缺的三件事：
1. **不用管理長期私鑰**——用 OIDC 身分換取短效憑證
2. **透明度日誌（Rekor）**——所有簽章公開記錄，無法悄悄替換
3. **可驗證的身分**——簽章綁定到「誰」（GitHub 帳號、Google 帳號）

## 三、本專案密碼學實作的誠實邊界

`rsa_sign.py` 是**教育實作**，以下都是它**沒有**做到的：

| 缺少的能力 | 影響 | 嚴重度 |
|---|---|---|
| **未經密碼學審查** | 可能存在未發現的缺陷 | 高 |
| **非常數時間實作** | 有計時側通道攻擊風險 | 中 |
| **無金鑰撤銷** | 私鑰洩漏後無法作廢 | 高 |
| **無憑證到期** | 憑證永久有效 | 中 |
| **RSA 而非 Ed25519** | 較慢、金鑰較大；PKCS#1 v1.5 有歷史包袱 | 低（技術上仍安全） |
| **無時間戳** | 無法證明「何時」簽的 | 中 |
| **無透明度日誌** | 無法偵測事後替換 | 中 |

### PKCS#1 v1.5 vs OAEP/PSS

本實作使用 PKCS#1 v1.5 填充（歷史最悠久、相容性最好），
但其**簽章版本**（RSASSA-PKCS1-v1_5）仍被視為安全，
而**加密版本**（RSAES-PKCS1-v1_5）已不建議使用（有 Bleichenbacher 類攻擊）。

現代建議是 **RSASSA-PSS**（機率式簽章）或直接用 **Ed25519**。

## 四、我們如何驗證自製實作是正確的

因為「自己驗自己」是循環論證，所以做了**獨立驗證**：

### 方法 1：不呼叫自己的驗證函式

用數學定義**重算**簽章結構：

```
PKCS#1 v1.5 結構完全符合 : True
  開頭                     : 0001
  DigestInfo 前置          : 3031300d060960864801650304020105000420
  標準 SHA-256 前置        : 3031300d060960864801650304020105000420
  🡒 與標準相符            : True
簽章長度 = k (256)         : True
公開指數 e = 65537         : True
```

### 方法 2：篡改測試

改動被簽章檔案的一個位元組 → 驗證必須失敗（實測 ✓ 失敗）。

### 方法 3：版本約束邏輯的單元測試

```
cmp_version('2.2', '2.2.0')     = 0   ✓（補零對齊）
cmp_version('3.1.9', '3.1.10')  = -1  ✓（不是字串比較）
satisfies('2.2.1', ==2.2.0)     = False ✓（★ 最關鍵）
satisfies('1.24.1', <1.24)      = False ✓
```

> **教訓**：自己寫的密碼學，至少要能通過「不依賴自己」的獨立檢查。
> 但即使通過，也不代表可以上生產環境——那只代表「沒有明顯錯誤」。

## 五、跨平台陷阱（實測記錄）

### Windows 的 `os.chmod` 無法設定 POSIX 權限

```python
os.chmod(path, 0o600)   # 實測仍顯示 0o666
os.chmod(path, 0o444)   # 只有唯讀位元有效
```

**影響**：在 Windows 上，`0o600` 這種「只有擁有者可讀寫」的保護**不會生效**。

**正確做法**：
1. Windows 上用 `icacls` 設定 ACL
2. 或改用集中式密鑰管理（KMS/Vault）——根本不需要管檔案權限
3. Linux 上才用 `os.chmod(path, 0o600)`

**這個陷阱在本專案被記錄下來，而不是被隱藏**——
先前 `loglab_patched.py` 曾把「權限 0o600」寫在註解但斷言不檢查，
那是不誠實的呈現，已修正（見 `S1c_a09_logging_alerting.md` §五）。

## 六、給學習者的三條實務原則

### 1. 不要自己寫密碼學（除非目的是學習）

```
學習目的 → 自己寫，理解機制（本專案的立場）
生產目的 → 用 libsodium / OpenSSL / cryptography / Sigstore
```

### 2. 私鑰的生命週期比演算法更常出問題

實務上供應鏈入侵很少是「演算法被破解」，
更常見的是：
- 私鑰被提交進版控
- 私鑰放在 CI 環境變數但被 echo 出來
- 私鑰權限過寬
- 沒有輪替與撤銷機制

> **本專案先示範了錯誤做法（明文金鑰），再說明正確做法**——
> 這比只講正確做法更有教學效果。

### 3. 「有簽章」不等於「安全」

| 問題 | 只做簽章夠嗎 |
|---|---|
| 私鑰洩漏 | ❌ 不夠（需 HSM + 輪替） |
| 簽章者身分不可信 | ❌ 不夠（需 PKI / OIDC 綁定） |
| 事後被替換 | ❌ 不夠（需透明度日誌） |
| 建置流程被入侵 | ❌ 不夠（需 reproducible build） |

**簽章是必要條件，不是充分條件。**
