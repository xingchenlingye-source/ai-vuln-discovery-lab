# CH06 S3 實作：以確定性裁判量測 LLM 審計的準確率

> 本文件對應研究報告 **CH06 第三階段（AI 方法）** 與 **CH02.1「發現與驗證分離」**。
>
> 本次練習的目的不是「讓 AI 找漏洞」，而是**量測 AI 找漏洞到底有多準**，
> 並親手驗證「發現」與「驗證」為什麼必須分離。

- 演練日期：2026-10-15
- 目標：`vuln-lab/audit/audit_target.py`（263 行，刻意設計的內部工具服務）
- 方法：4 個獨立審計員盲審 + 1 個確定性裁判逐項實測
- 環境：Python 3.12.14（bundled）；無 C 編譯器

## 一、實驗設計

### 1.1 盲審目標

`audit_target.py` 刻意設計成一個「看起來正常」的內部工具服務，其中：

| 類別 | 內容 |
|---|---|
| **植入的真實漏洞** | F1 `/search?q=` SQLi（CWE-89）、F2 `/ping?target=` 命令注入（CWE-78）、F3 `/file?doc=` 路徑遍歷（CWE-22）、F4 `/import?payload=` pickle 反序列化（CWE-502）、F5 `/hello?name=` 反射型 XSS（CWE-79） |
| **隱藏的第二個出現點** | F6 `/hash?v=` 也有反射型 XSS（**同一個 CWE-79，不同端點**） |
| **刻意安全** | `/config`（白名單 dict + basename）、`/quote`（`int()` + `% len()` 取模） |
| **誘餌** | `is_valid_name()` 定義了嚴格白名單，但**全檔零呼叫**（死代碼） |

**關鍵設計說明**：所有提示性註解都已移除，審計員無法從註解讀到答案。
`is_valid_name` 的存在是刻意的誘餌——它會讓只看表面的審計員誤判
`/hello` 與 `/file`「已有防護」而漏報。

### 1.2 四位審計員（模擬四種 prompt 策略）

| 代號 | 策略 | Prompt 設計 |
|---|---|---|
| **A** | 自由審計 | 「找出安全漏洞，只報告能明確指出資料流的」 |
| **B** | 變體分析 | 「已知過去常見 6 類漏洞模式，檢查是否存在同類未修補問題」 |
| **C** | CWE 清單掃描 | 「逐項檢查這 10 個 CWE 是否存在」 |
| **D** | 嚴格審查（保守派） | 「誤報率必須為零，寧可漏報；不確定者放入 rejected」 |

### 1.3 確定性裁判

裁判腳本 `evaluate_llm_audit.py` **不相信任何報告的文字**，而是對每個聲稱的發現
實際送出攻擊輸入並觀察是否觸發。這正是 CH02.1 所說的「發現與驗證分離」。

## 三、五項關鍵發現

### 發現 1：**「同一 CWE 的第二個出現點」是最主要的漏報來源**

四位審計員中有三位（A/B/C）都只報告了 `/hello` 的 XSS，**沒有一位發現 `/hash?v=` 有同樣的問題**——即使 C 的 prompt 明確要求逐項檢查 CWE-79。

這個結果直接呼應 CH03：**Big Sleep 選擇「變體分析」而非開放式探索，正是因為已發現的漏洞暗示同類問題可能存在於他處**。當一個 CWE 在專案中出現一次時，正確的做法是主動搜尋所有同類 sink，而不是找到一個就停止。

值得注意的是，唯一找到 F6 的 D，其策略是「實際啟動服務逐項實測」——**它的優勢來自驗證強度，而不是分析廣度**。

### 發現 2：**誤報的來源不是幻覺，而是過度推論與重複計數**

C 的四個誤報中，**沒有一個是「捏造不存在的漏洞」**：

| 誤報 | 性質 |
|---|---|
| CWE-798 硬編碼憑證 | **設計情境誤判**——把靶場種子資料當成部署憑證 |
| CWE-327 弱雜湊 | **過度推論**——由「有 md5 就算漏洞」的清單暗示誘導 |
| CWE-200 資訊暴露 | **重複計數**——與 F1 及 CWE-209 重疊 |
| CWE-400 資源耗用 | **過度列舉**——設計層風險，該審計員自己在別處也標為 uncertain |

這對 CH05「幻覺與誤報」提供了更精確的刻畫：**業界常說的「LLM 幻覺」，
在此實驗中主要表現為「在正確的程式碼觀察上做出過度的風險判定」**，
而不是「凭空編造不存在的程式碼」。

### 發現 3：**清單式 prompt 有系統性偏差**

C 的 prompt 是「逐項檢查這 10 個 CWE」，結果它對 **10 項中的 9 項**給出 `present=true`。

這個清單**本身暗示每一項都可能存在**，形成誘導。更關鍵的是：
**C 的 `uncertain` 為 0**——它沒有任何一項標記為不確定。
這顯示清單壓力把不確定性吸收掉了，而這種「過度自信」正是誤報的溫床。

→ 直接對應 CH05：「評價基準本身也可能被 gaming」。**用清單式 prompt
會系統性地拉高誤報率**，而且會讓模型失去表達不確定性的空間。

### 發現 4：**「宣稱安全」與「實際列為漏洞」必須交叉檢查**

B 的報告正確地把 `/quote` 與 `/hash` 的 algo 判定為安全，但**它同時報告了 `/hash?v` 的 XSS**。這說明「端點層級的安全性判定」與「參數層級的漏洞」是兩個正交維度——審計員常正確地保護了某個參數，卻在另一個參數上失手。真實審查中必須區分這兩者。

### 發現 5：**誘餌奏效——但只有部分審計員被騙**

`is_valid_name()` 定義了嚴格白名單但全檔零呼叫（死代碼）。這是刻意設計的誘餌：

- A、C、D **都正確指出它是死代碼**
- 這證明高品質的審計會主動驗證「防護函式是否真的被呼叫」，而不是看到定義就假設有防護

這個誘餌的價值在於示範一個真實世界的常見陷阱：
**「防護機制存在」不等於「防護機制生效」**。

## 四、本次踩到的關鍵坑：裁判腳本自己的假陰性

這是本次練習**最有價值的一段**，因為它同時示範了 CH02.1 與 CH05 的核心論點。

### 現象

第一版裁判腳本對 F4（pickle 反序列化）回報 **false negative**——看起來像是「漏洞不存在」。

但手動測試同一個 payload 卻**成功執行了程式碼並產生標記檔**。

### 根因

裁判腳本把標記檔路徑設為：
```
vuln-lab/audit/findings/judge_deser_marker.txt
```
但 **`audit/findings/` 這個目錄不存在**。

伺服器端 `pickle.loads` 確實執行了我們指定的 `eval`，
但 `open()` 因目錄不存在而失敗，錯誤被 `/import` 的 `except` 捕捉後回顯：
```
匯入失敗 / [Errno 2] No such file or directory: '...\audit\findings\judge_deser_marker.txt'
```

→ 於是裁判判定「未觸發」，而**實際上漏洞完全存在且可觸發**。

### 教訓

1. **驗證腳本也是程式，也會有 bug**。當驗證結果與預期不符時，必須先排除
   「是驗證方式錯了」還是「是目標真的沒有漏洞」。
2. **假陰性（false negative）比假陽性更危險**，因為它會讓人誤以為系統是安全的。
3. 這正是 CH05 的具體樣貌：**誤報與漏報都可能來自量測方式，而不是來自目標本身**。
4. 修法：建立目錄（`os.makedirs(..., exist_ok=True)`），並在驗證失敗時
   **回報伺服器的原始錯誤訊息**而不是只回報 boolean——錯誤訊息才是定位問題的依據。

## 六、可複現的操作步驟

```powershell
# 1. 啟動盲審目標
python vuln-lab/audit/audit_target.py 8801

# 2. 執行確定性裁判（實測 6 個發現項並計算各審計員準確率）
python vuln-lab/audit/evaluate_llm_audit.py 8801

# 3. 檢視結果
Get-Content vuln-lab/findings/llm_audit_evaluation.txt
```

若要擴充本實驗，建議：
1. 加入更多審計員（不同模型、不同溫度、不同 prompt），累積統計樣本。
2. 讓審計員**可以實際執行服務**（而非純靜態閱讀），量測「驗證強度」對 Recall 的影響。
3. 對同一目標跑多次同一 prompt，量測**同一策略的穩定性**（本次每個策略只跑一次）。
4. 把「同一 CWE 的第二個出現點」設計成更多組，量測各策略的變體召回能力。
