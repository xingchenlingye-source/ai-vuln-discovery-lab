## 一、為什麼這兩類特別值得練

先前靶場（authlab、authlab2、loglab）涵蓋的是
「**實作層**缺陷」——少一個檢查、錯誤處理方向錯了、日誌沒寫。

A06 與 A04 則不同：

| | 實作層缺陷 | **A06 設計缺陷** | **A04 加密缺陷** |
|---|---|---|---|
| 例子 | IDOR、fail-open | 限購可繞過、價格由客戶端決定 | 弱雜湊、弱隨機 |
| 修補方式 | 補上檢查 | **改變設計** | **換演算法/機制** |
| 能否靠「更努力寫程式」避免 | 可以 | **不行**（需要重新設計） | 需要正確的知識 |

> **A06 的核心洞察（官方強調）**：
> 「設計層缺陷無法靠實作修補」——
> 就算程式寫得完美，如果限購規則的**定義**就是錯的，漏洞依然存在。

## 二、六個漏洞

| # | 漏洞 | OWASP | CWE | 觸發方式 |
|---|---|---|---|---|
| B1 | 限購可繞過（check-then-act） | **A06** | CWE-799 / CWE-362 | 重複呼叫 `/buy` 繞過「每人限購 1 件」 |
| B2 | **TOCTOU 競態**（超額扣款） | **A06** | CWE-367 | 併發 3 筆扣款，餘額 5000 卻扣了 12000 |
| B3 | 價格由客戶端提供 | **A06** | CWE-472 | `/buy?price=1` 讓 100 元商品變 1 元 |
| B4 | MD5 無 salt 儲存密碼 | **A04** | CWE-916 | `md5('123456')` 可反查 |
| B5 | 可預測的隨機 token | **A04** | CWE-338 | 注入相同 seed 產生相同 token |
| B6 | 敏感資料明文儲存 | **A04** | CWE-311 | `/cards` 直接顯示完整卡號與餘額 |

## 三、驗證結果（漏洞版 6/6）

### 最有力的證據：B2 競態

```
餘額 5000，併發送出 3 筆 4000 元扣款
→ 成功 3 筆，最終餘額 = −7000
```

**餘額被扣成負 7000**——這是金融系統的典型嚴重缺陷。
單次請求永遠看起來正常，**只有併發才能觀察到**。

### 驗證方式的三種型態（再次印證 CH02.1）

| 漏洞類型 | 驗證方式 | 本次對應 |
|---|---|---|
| 注入類 | 看 HTTP 回應 | （前次練習） |
| 日誌類 | 檢查日誌檔案 | （A09 練習） |
| **競態類** | **必須併發請求** | **B1、B2** |
| 加密類 | 已知值反查／重現性測試 | B4、B5 |

> **驗證方式必須配合漏洞類型**——這是本專案反覆出現的主題。

## 四、修補實作：A06 重點在「改變設計」

| 漏洞 | 修補方式 | 性質 |
|---|---|---|
| B1 | 限購以「**所有訂單**」計算（不再只看 `paid=1`）＋ **資料庫唯一約束** | 改變規則 + 結構保證 |
| B2 | 改為**單一原子 UPDATE**：`WHERE balance >= ?` 並檢查 `rowcount` | **改變機制** |
| B3 | **移除**價格參數，一律由伺服器從 DB 查 | 修正信任邊界 |
| B4 | PBKDF2-HMAC-SHA256 + per-user salt（20 萬次） | 換演算法 |
| B5 | `secrets.token_urlsafe(32)`（CSPRNG），並**拒絕任何 seed 注入** | 換隨機源 |
| B6 | 卡號加密儲存，只回末四碼 | 改變儲存方式 |

### 修補驗證結果

```
B1 限購無法繞過          成功 1/3（原 3/3）
B2 併發扣款不超額        成功 1/3（原 3/3，餘額 −7000）
B3 價格由伺服器決定      單價 = 100（原 1）
B4 改用 PBKDF2 + salt    md5 不再出現、含 salt
B5 token 不可預測        拒絕 seed、長度 43、兩次不同
B6 卡號加密儲存          完整卡號不再出現、僅末四碼

攻擊失效 : 6/6 ✓      功能保留 : 4/4 ✓
```

### 修補的關鍵設計原則

**B2 的修補最值得記住**：

```python
# ❌ 漏洞版：檢查與扣款分離
cur.execute("SELECT balance FROM cards WHERE user_id=?", (uid,))
if balance < amount: return error
# ← 這裡可被穿插！
cur.execute("UPDATE cards SET balance = balance - ? WHERE user_id=?", (amount, uid))

# ✅ 修補版：檢查與扣款合為單一原子操作
cur.execute("UPDATE cards SET balance = balance - ? "
            "WHERE user_id = ? AND balance >= ?", (amount, uid, amount))
if cur.rowcount != 1: return error      # 資料庫保證了原子性
```

> **不要用「先檢查再動作」實作並發安全**——
> 要把檢查條件放進**動作本身**，讓資料庫（或鎖）保證不可分割。

## 八、A03 的剩餘缺口（誠實記錄）

本次焦點是 A04/A06。A03 供應鏈雖已「充分」，但仍有下列缺口：

| 缺口 | 現況 | 為何未做 |
|---|---|---|
| **間接依賴樹** | 只掃 requirements.txt | 需完整安裝依賴樹或解析 lock 檔 |
| **非對稱簽章** | 只有 HMAC（對稱） | 需金鑰管理；標準庫可做但複雜 |
| **信任鏈 / PKI** | 無 | 需憑證基礎設施 |
| **CycloneDX schema 驗證** | 無 | 需官方 schema |
| **CI 整合** | 無 | 需 CI 環境 |

其中**非對稱簽章**最值得補——因為它是「來源可信」的唯一途徑，
HMAC 只能做到「完整性」（見 `sbom.py` 的邊界說明）。
