# S1 補充：SSRF（伺服器端請求偽造）

> 補上課程**最大模組**（10 集）、也是本專案完全沒有的類別。
>
> 對應研究報告 **CH06 S1** 與 **CWE-918**。

- 日期：2026-10-15
- 靶場：`ssrflab/`（雙埠架構：主應用 + 內部服務）
- **驗證結果：6/6 全部通過**

---

## 一、為什麼這是重大缺口

課程 **84 集／21 模組**中，對照本專案發現 **13 個模組完全未涵蓋**。
其中 **SSRF 用了 10 集**（P20–P22、P44–P50），是課程**最大的單一主題**。

**為什麼 SSRF 在雲環境下特別危險**：

```
應用有 SSRF  →  可讀雲端 metadata（169.254.169.254）
             →  取得**臨時憑證**
             →  等同接管該雲端角色
             →  可能讀寫整個雲帳號資源
```

> 這就是為什麼 SSRF 被視為雲環境的**首要風險之一**——
> 它不是「讀一個頁面」，而是「拿到鑰匙」。

## 二、靶場架構（雙埠設計）

```
┌──────────────────┐   SSRF    ┌────────────────────────┐
│ 主應用 :8925      │ ────────▶ │ 內部服務 :8926          │
│ GET /fetch?url=  │           │  · /internal/admin      │
│ GET /fetch-safe  │           │  · /latest/meta-data/…  │
│ GET /redirect    │           │  · /health              │
└──────────────────┘           └────────────────────────┘
```

**安全邊界**：內部服務也是**本機另一個埠**；metadata 是**本機假端點**；
所有 URL 只指向 `127.0.0.1`——**完全不出本機、不連網際網路**。

## 三、五種手法與驗證結果

| # | 手法 | CWE | 結果 |
|---|---|---|---|
| S1 | **直接存取內網服務**（無防護） | CWE-918 | ✅ |
| S2 | **白名單邏輯可被繞過** | CWE-918 | ✅ |
| S3 | **302 重導向繞過驗證** | CWE-918 | ✅ |
| S4 | **讀取雲端 metadata 憑證** | CWE-918 / CWE-522 | ✅ |
| S5 | 內部服務無認證（橫向移動） | CWE-306 | ✅ |
| — | **安全對照**：`/fetch-safe` 正確阻擋 | 防護驗證 | ✅ |

### S1：最直接的證據

```
GET /fetch?url=http://127.0.0.1:8926/internal/admin
→ 伺服器代替我們連內網，回傳內部管理頁
   內容含：FLAG、資料庫連線字串、Redis 位址
```

### S4：雲端憑證（本靶場最嚴重的後果）

```
GET /fetch?url=…/latest/meta-data/iam/security-credentials/SSRFLab-EC2-Role
→ 回應含 AccessKeyId / SecretAccessKey / Token
```

⚠ **這是本機模擬的假端點**（`AsiaFake…`）。真實環境中此端點會回傳**可用的**憑證。

### S3：重導向繞過的機制

```
驗證只檢查「第一次請求的 URL」（看起來合法）
  → 目標回 302 到內網
  → 解析器**自動跟隨**，驗證被繞過
```

### S2：白名單的典型錯誤實作

```python
host_part = re.match(r'^https?://([^/]+)', url).group(1)
if any(host_part.startswith(a) for a in ['public.example.com']):
    通過
```

**靜態分析結果**：

| 變體 | 通過白名單 | 實際連線目標 | 是否內網 |
|---|---|---|---|
| 原樣 | True | public.example.com | False |
| 大寫 | False | PUBLIC.EXAMPLE.COM | False |
| 尾點 | True | public.example.com. | False |
| **userinfo(@)** | **True** | **127.0.0.1:8926** | **True ★** |
| 八進位 IP | False | 0177.0.0.1 | True |

**`userinfo@` 變體同時滿足「通過白名單」與「實際連到內網」** → 繞過成立。

## 四、★ 實測發現：標準庫的實作限制（誠實記錄）

測試過程中發現一件重要的事：

```
帶 userinfo（user@host）的 URL 在 Python 標準庫 urllib 上
→ RemoteDisconnected: Remote end closed connection without response
```

**這不是漏洞不存在**，而是 **Python `urllib` 的實作限制**。
真實世界用 `curl`、`requests`、瀏覽器時，`@` 手法確實有效。

**因此我把 S2 的驗證改為「靜態分析白名單邏輯 + 變體測試」**，
而不是硬要它在標準庫上「打成功」——**這比假裝攻擊成功更誠實**。

> 這與本專案先前多次遇到的情況一致：
> **驗證方式的限制必須被揭露，而不是被隱藏。**

## 五、SSRF 的驗證特色（第七種型態）

本專案現在累積了**七種驗證型態**：

| # | 漏洞類型 | 驗證要看什麼 |
|---|---|---|
| 1 | 注入（SQLi/CMDi） | HTTP 回應內容 |
| 2 | 日誌類（A09） | 日誌與告警檔案 |
| 3 | 競態類（A06） | **併發請求** |
| 4 | 加密類（A04） | 已知值反查 |
| 5 | 設定類（A02） | **回應標頭** |
| 6 | XSS/CSRF/XXE | 未轉義標籤／缺少的防護／實體展開 |
| **7** | **SSRF** | **伺服器願不願意替你連到不該連的地方** |

> SSRF 的驗證既不看回應格式、也不看防護機制，
> 而是看**伺服器的行為**——「它替我們連到哪裡了」。

## 六、修補方向

| 手法 | 修補 |
|---|---|
| S1 | 解析真實主機名 → 阻擋私有／link-local IP |
| S2 | **不要用字串比對主機**；正規化後取 `p.hostname` 再驗證 IP 類別 |
| S3 | 關閉自動跟隨重導向，或**每一跳都重新驗證** |
| S4 | 強制 **IMDSv2**（需 token 才能讀 metadata）；網路層限制 |
| S5 | 內部服務仍需認證（**零信任**）；網路分段；最小權限 |

**本靶場的 `/fetch-safe` 示範了正確做法**：

```
(a) 解析真實主機名 → (b) 判斷是否為私有/link-local IP → (c) 白名單比對
→ 實測：HTTP 403「禁止存取私有／內部位址」
```

## 七、開發時踩到的 bug（三個，都是同一類）

### Bug 1+2：`PAGE` 與 `INTERNAL_PAGE` 的 CSS 大括號未轉義

```
KeyError: 'font-family'
```

**這是我第三次踩到這個坑**（`frontendlab`、`xsslab`、現在 `ssrflab`）。

原因：`str.format()` 會把 CSS 的 `{font-family:...}` 當成佔位符。

### Bug 3：我的修復工具「修過頭」

用工具批次轉義大括號時，**把真正的佔位符 `{body}` 也轉義成了 `{{body}}`**——
結果頁面顯示字面的 `{body}` 而不是內容。

**兩個教訓**：
1. **同一個坑踩三次**——這說明我應該建立一個可重用的樣板函式，
   而不是每次手寫 HTML 模板
2. **自動修復工具必須驗證結果**——我驗證後才發現佔位符被誤轉義
