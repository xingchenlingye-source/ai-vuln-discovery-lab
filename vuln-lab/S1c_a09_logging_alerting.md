## 一、為什麼 A09 特別值得練

A09 在 2025 版**改名**：從「Security Logging and **Monitoring** Failures」
變成「Security Logging and **Alerting** Failures」。

這個改名點出了核心：
> **「有記錄」不等於「有人會知道」。**

A09 涵蓋三個官方面向：
1. 無法偵測入侵 / 事件回應不足
2. 缺乏審計日誌與監控
3. 日誌本身不安全（含敏感資料、未保護、未告警）

### 與注入類漏洞的根本差異

| | 注入類（SQLi/XSS） | A09 |
|---|---|---|
| 漏洞在哪 | **回應裡** | **日誌與告警檔案裡** |
| 驗證方式 | 看 HTTP 回應 | 檢查「系統有沒有留下證據」 |
| 修補驗證 | 攻擊輸入失效 | **缺口補上**（日誌確實記了、告警確實發了） |

> 這是本次練習最重要的方法論收穫：
> **A09 的驗證必須檢視日誌檔，而不是回應內容。**

## 二、六個缺口

| # | 缺口 | CWE | 觸發／觀察方式 |
|---|---|---|---|
| L1 | 登入失敗不記錄 | CWE-778 | 失敗登入後比對日誌（無變化） |
| L2 | 關鍵操作無審計軌跡 | CWE-778 | 改角色後查 audit 表（0 筆） |
| L3 | 日誌含**明文密碼** | CWE-532 | 登入成功後日誌出現 `password=123456` |
| L4 | 暴力破解無告警 | CWE-778 | 12 次失敗後 /alerts 為空 |
| L5 | 日誌檔可被 API 清除 | CWE-732 | `/log?clear=1` 直接清空 |
| L6 | 無 request_id | CWE-778 | 每個事件是獨立純文字行，無法串連 |

### 最反諷的設計（真實世界的常見錯誤）

漏洞版的行為是：

```
攻擊者看到的 ：「失敗次數：7（僅顯示，未記錄、未告警）"
防禦者看到的 ：（日誌裡什麼都沒有）
```

**攻擊者有進度資訊，防禦方零資訊——完全反了。**
這正是 A09 的典型樣貌：不是「沒有安全機制」，而是「機制的方向錯了」。

## 四、修補實作

| 缺口 | 修補方式 |
|---|---|
| L1 | 成功與失敗**都**記錄（含 actor、result、reason） |
| L2 | 寫入審計表（actor / action / target / result / request_id） |
| L3 | 敏感欄位遮罩：`12****(len=6)`，**永不記錄明文** |
| L4 | 同一帳號失敗達 5 次 → 產生 `possible_brute_force` 告警；**並移除回應中的嘗試次數** |
| L5 | 移除清除端點（回 403 並記錄該嘗試）；日誌權限收緊 |
| L6 | 結構化 JSON Lines + 每個請求一個 `request_id` |

### 修補後的實際日誌

```json
{"ts": "2026-10-15T15:50:41", "request_id": "2f2b15934690",
 "event": "login", "actor": "alice", "result": "success",
 "password_masked": "12****(len=6)"}
```

### 修補後的告警

```json
{"ts": "2026-10-15T15:50:41", "request_id": "86b6c5dc3816",
 "alert": "possible_brute_force", "severity": "high",
 "detail": "user=admin failures=7"}
```

### 修補驗證結果

```
缺口補上 : 6/6 ✓
功能保留 : 4/4 ✓  （正常登入、角色變更、日誌讀取、審計查詢）
```

## 五、實作時踩到的三個陷阱（最有價值的部分）

### 陷阱 1：測試順序污染（false negative）

第一次執行時 **L3 顯示「未觸發」**，但漏洞明明存在。

**原因**：驗證腳本把 L3 放在 L1 之後，而 L1 會執行 `/log?clear=1` 清空日誌，
L3 讀到的自然是空檔案。

**修正**：把 L3 移到**最後**執行，並在程式碼中註明原因。

> **教訓**：多個測試共用狀態時，執行順序會影響結果。
> 這與報告 CH05 的論點一致——**量測方式決定你看見什麼**。

### 陷阱 2：測試設計錯誤（把「想驗證的字串」當成「有效憑證」）

修正順序後 **L3 仍然失敗**（HTTP 401）。

**原因**：我用 `MySecretPassword123` 當登入密碼，但**那不是 alice 的真實密碼**。
靶場的邏輯是「登入成功才記錄密碼」，登入失敗自然不寫日誌——
**是我自己的測試用錯了密碼**，卻誤以為是漏洞不存在。

**修正**：改用正確密碼 `123456` 讓登入成功，再檢查日誌是否出現明文。

> **教訓**：兩次 false negative **都來自測試腳本，而不是目標本身**。
> 這正是報告 CH02.1「發現與驗證分離」的實務印證——
> 驗證腳本本身的錯誤，會製造出「漏洞不存在」的假象。

### 陷阱 3：跨平台權限假象（誠實性問題）

修補版用 `os.chmod(LOG_PATH, 0o600)` 收緊權限，驗證報告卻顯示 `0o666`。

**診斷**：Windows NTFS **只有唯讀位元**，`os.chmod(0o600)` 與 `0o644` 都不生效
（實測兩者皆為 `0o666`，只有 `0o444` 有效）。

**更重要的問題是**：我原本的驗證腳本把「權限 0o600」寫進**註解**，
但**斷言只檢查 HTTP 403**——這是**不誠實的呈現**：
報告看起來「權限已收緊」，實際上根本沒生效。

**修正**：
1. 把權限**從斷言中移除**，並明確寫出「這是平台限制、不列入驗證」
2. 在 `loglab_patched.py` 註解中說明 Windows 的正確替代方案
   （`icacls` 設定 ACL、集中式日誌）
3. 保留 Linux 語意的程式碼並附註，而不是假裝它已經生效

> **教訓**：**不要用一個永遠「看似通過」的檢查來假裝達成了某件事。**
> 平台限制應該被揭露，而不是被隱藏。
