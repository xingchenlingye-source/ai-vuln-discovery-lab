## 二、缺口 1：間接依賴樹

### 為什麼重要

`scan_deps.py` 只掃 `requirements.txt` 的**直接依賴**。
但真實供應鏈風險主要來自**間接依賴**——你沒直接引入的套件。

**Log4Shell（CVE-2021-44228）** 就是典型案例：
許多專案從未直接引入 `log4j-core`，而是透過 `spring-boot-starter-logging` 進來。

### 實測結果

```
直接依賴：8 個（requirements-vulnerable.txt 的 8 行）
展開節點：17 個
間接依賴：9 個（爆炸倍數 2.1 倍）

間接依賴清單：
  · certifi        (由 requests 引入)
  · chardet        (由 requests 引入)
  · idna           (由 requests 引入)
  · click          (由 Flask 引入)
  · itsdangerous   (由 Flask 引入)
  · MarkupSafe     (由 Jinja2 引入)
  · pytz           (由 Django 引入)
  · sqlparse       (由 Django 引入)
  · Werkzeug       (由 Flask 引入)
```

> **你的 requirements.txt 只有 8 行，但實際依賴樹有 17 個節點。**
> 攻擊者只需要**其中一個**間接依賴有漏洞即可。

### 誠實記錄的限制

部分套件（PyYAML 5.1、cryptography 2.6.1、lxml 4.3.0）的 metadata 取得失敗
（`No matching distribution found`——舊版本已從 PyPI 下架或無對應 wheel）。
且**間接依賴的版本未定**，因此無法逐一查詢 OSV。

真實工具（`pip-audit`、`osv-scanner`）會解析**已安裝環境**的實際版本，
不受此限。本工具以 `pip download` 取 metadata，是輕量替代方案。

## 三、缺口 2+3：非對稱簽章與信任鏈

### 為什麼 HMAC 不夠

`sbom.py` 用 HMAC-SHA256，但 HMAC 是**對稱式**：

```
驗證者必須持有同一把密鑰
  → 所以驗證者也能偽造簽章
  → 「來源可信」根本無法成立
```

在供應鏈場景下這是致命的：你要證明「這個 SBOM 是我發的」，
但驗證者拿到密鑰後也能產出一模一樣的簽章。

### 非對稱簽章的解法

```
私鑰（只有發佈者持有）→ 簽
公鑰（公開給所有人）  → 驗
驗證者無法用公鑰產出有效簽章 → 能證明「只有私鑰持有者能發這個」
```

### 本實作（純標準庫）

| 元件 | 實作 |
|---|---|
| 質數產生 | Miller-Rabin（40 輪） |
| 金鑰 | RSA-2048，e = 65537 |
| 填充 | PKCS#1 v1.5 / EMSA-PKCS1-v1_5 |
| 雜湊 | SHA-256（標準 DigestInfo 前置） |
| 信任鏈 | 根 CA 私鑰簽發佈者憑證（公鑰+身分）→ 發佈者簽 SBOM |

### 驗證結果

**完整信任鏈（三步）**：

```
步驟 1  憑證是否由根 CA 簽發 : ✓ 是
步驟 2  從憑證取得發佈者公鑰 : ✓（n 為 2048 bits）
步驟 3  檔案簽章驗證         : ✓ 通過
        檔案雜湊一致         : ✓

根 CA（信任錨） → 發佈者憑證 → SBOM 簽章 → 檔案內容
```

**篡改測試**：改動 sbom.json 後 → 步驟 3 **✗ 失敗**、雜湊 **✗ 不一致**。

### 獨立正確性驗證（避免「自己驗自己」）

我另外寫了一個**不呼叫 `rsa_sign.py` 驗證函式**的檢查，
純用數學定義重算簽章結構：

```
PKCS#1 v1.5 結構完全符合 : True
  開頭                     : 0001
  DigestInfo 前置          : 3031300d060960864801650304020105000420
  標準 SHA-256 前置        : 3031300d060960864801650304020105000420
  🡒 與標準相符            : True
  雜湊尾端相符             : True
簽章長度 = k (256)         : True
公開指數 e = 65537         : True

結論：簽章符合 RFC 8017 PKCS#1 v1.5 + SHA-256 標準 ✓
```

> **為什麼要做這個**：自己寫的簽章用自己寫的驗證函式通過，
> 是**循環論證**。獨立的數學重算才有說服力。

### ⚠ 誠實邊界（必讀）

| 項目 | 說明 |
|---|---|
| **未經密碼學審查** | 這是教育實作，不是 production-ready |
| **非常數時間** | 有計時攻擊風險 |
| **無金鑰撤銷** | 缺少 CRL / OCSP |
| **無憑證到期** | 憑證永久有效 |
| **建議演算法** | 真實系統應用 Ed25519 或 ECDSA，而非 RSA-2048 |
| **建議工具** | Sigstore/cosign（含透明度日誌 Rekor）、OpenSSL、libsodium |

## 四、缺口 5：統一驗證管線（整合五種驗證型態）

### 為什麼需要

先前 6 個靶場「各跑各的」，而每個靶場的**驗證方式都不同**。

### 五種驗證型態

| 靶場 | 型態 | 驗證要看什麼 |
|---|---|---|
| authlab | ① 注入類 | HTTP **回應內容** |
| authlab2 | ② 認證類 | 回應 + 資料庫狀態 |
| loglab | ③ 日誌類 | **日誌與告警檔案** |
| buyLab | ④ 競態類 + 加密類 | **併發請求** + 已知值反查 |
| configlab | ⑤ 設定類 | **回應標頭** + 允許的方法 |

### 實測結果：9/9 全部通過

```
▶ authlab          （漏洞版）  ✓ 漏洞存在 6/6
▶ authlab2         （漏洞版）  ✓ 漏洞存在 7/7
▶ loglab           （漏洞版）  ✓ 漏洞存在 6/6
▶ buyLab           （漏洞版）  ✓ 漏洞存在 6/6
▶ configlab        （漏洞版）  ✓ 漏洞存在 6/6
▶ authlab-patched  （修補版）  ✓ 修補驗證 12/12（2 組條件）
▶ loglab-patched   （修補版）  ✓ 修補驗證 10/10（2 組條件）
▶ buyLab-patched   （修補版）  ✓ 修補驗證 10/10（2 組條件）
▶ configlab-patched（修補版）  ✓ 修補驗證 11/11（2 組條件）

通過 9 / 9
```

**統計**：漏洞版共驗證 **31 個漏洞存在**；修補版共 **43 項條件通過**。

### 管線的技術要點

1. **自動選擇空閒埠**（避免與其他服務衝突）
2. **自動啟停靶場**（`Popen` + `terminate`，`finally` 保證清理）
3. **解析兩種輸出格式**（漏洞版的「共 N/M」與修補版的「攻擊失效 N/M」）
4. **非零結束碼**（供 CI 判斷）

### 開發時踩到的 bug（值得記錄）

第一次執行顯示**全部 9 個靶場「檔案不存在」**。

**原因**：`run_all.py` 位於 `vuln-lab/`，`HERE` 就是 lab 根目錄，
但我把 `LAB = os.path.dirname(HERE)` 設成了**父目錄**。

```
錯誤：vuln-lab/../authlab/     → 不存在
正確：vuln-lab/authlab/        → 存在
```

> 教訓：**相對路徑的基準點要先確認清楚**。
> 這類 bug 的特徵是「一次全部失敗」而不是「零星失敗」——
> 看到「全部都錯」時，先懷疑路徑或環境，而不是懷疑每個測試。

## 五、缺口 4：CI 整合

建立兩個 GitHub Actions workflow：

### `supply-chain-ci.yml`

| Job | 內容 |
|---|---|
| `dependency-scan` | 展開依賴樹 + OSV 掃描 + 上傳報告 |
| `sbom-and-sign` | 產生 CycloneDX SBOM → 產生金鑰 → 簽章 → **驗證信任鏈** |
| `verification-pipeline` | 執行 `run_all.py`（9 個靶場） |
| `scheduled-rescan` | **每週一 03:00 排程重掃** |

**為什麼要排程重掃**——這是 A03 的核心要求：

> **今天通過不代表下週通過，因為新的 CVE 每天都在公布。**

### `dependency-watch.yml`

在 PR 更動相依性檔案時觸發，把「相依性變更」本身視為**需要審查的事件**。

這對應 Shai-Hulud npm 蠕蟲的手法：
**相依性檔案被改動 → 引入新的（惡意）套件版本**。
所以「鎖定檔與清單的變更」應該是 CI 的告警點，而不是自動通過。

### 重要註記（寫在 workflow 內）

```yaml
# ★ 真實 CI 中，「私鑰」必須來自 secrets，絕不可進版控
#   本專案為教學示範，故金鑰為執行時即時產生。
#   - name: Sign with Cosign (production)
#     run: cosign sign-blob --key env://COSIGN_KEY sbom.json
```
