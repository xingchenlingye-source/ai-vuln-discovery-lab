## 二、帳號接管全鏈（A1–A6，6/6）

### 靶場設計：完整的攻擊鏈

```
A1 使用者列舉  →  找出有效帳號
        ↓
A2 token 可預測 →  自行算出重置 token（不需收信！）
        ↓
A3 token 可重放 →  一次取得，長期使用
        ↓
A4 舊 session 存活 →  受害者改密碼也踢不掉攻擊者
        ↓
A5 改密碼免舊密碼 →  取得任何觸發途徑即可永久接管
        ↓
A6 Host 標頭注入 →  釣魚信件中的連結被導向攻擊者
```

### 實測結果

| # | 漏洞 | CWE | 驗證證據 |
|---|---|---|---|
| A1 | 使用者列舉 | CWE-204 | 註冊回「使用者已存在」、找回回「查無此使用者」 |
| A2 | **token 可預測** | CWE-330/640 | **自行算出 token 並成功重置密碼** |
| A3 | token 可重放 | CWE-613 | 同一 token 用兩次都成功 |
| A4 | 舊 session 存活 | CWE-613 | 改密碼後舊 session 仍可存取 |
| A5 | 改密碼免舊密碼 | CWE-620 | 不含 `old_password` 仍成功 |
| A6 | **Host 標頭注入** | CWE-640 | 連結被導向 `evil.example.com` |

### ★ A2 的驗證方式最值得記錄

**不是看程式碼註解，而是證明攻擊者真的能預測**：

```
1. 取得 token 與 timestamp
2. 自己計算 md5("alice" + timestamp)
3. 比對 → 完全相符
4. 用算出的 token 實際重置密碼 → 成功
5. 用新密碼登入 → 成功
```

**實測輸出**：
```
回傳 token     : c8148676ab4a58a5a13fce92fb9d0bcd
timestamp      : 1792058335
自行計算 md5   : c8148676ab4a58a5a13fce92fb9d0bcd   ← 相符
用推算 token 重置成功 = True
用新密碼登入成功     = True
```

> **這才是「token 可預測」的完整證明**——
> 攻擊者**完全不需收到信件**就能接管任意帳號。

### A4 的實務意義

```
攻擊者登入 → 取得 session
受害者「發現被入侵」→ 改密碼
攻擊者用舊 session → 仍然有效 ★
```

> **改密碼無法把攻擊者踢出去**——受害者以為已經安全，實際上攻擊者仍持續存取。

## 三、短信轟炸（B1–B2，2/2）

### 自建模擬 SMS 閘道

因為無法接真實簡訊服務，我**自己實作了 SMS 閘道**（連接埠 8941）：

```
/send?phone=...        ★ 無速率限制（漏洞版）
/send-safe?phone=...   60 秒一次（正確對照）
/verify?phone=&code=   ★ 無嘗試次數上限
/log                   觀察記錄
```

### 實測結果

**B1 短信轟炸**：
```
連續 6 次 GET /send?phone=13800138000
回應碼：[200, 200, 200, 200, 200, 200]   ← 全部成功

安全對照 /send-safe：
  第 1 次 → 200
  第 2 次 → 429（已限制）✓
```

**B2 驗證碼可爆破**：
```
連續 8 次送錯誤驗證碼 → 全部回 401（無鎖定）
6 位數 = 100 萬種組合；若為 4 位數僅 1 萬種 → 數分鐘可完成
```

> **注意**：這是**模擬**簡訊（不真的發送）。
> 但漏洞的**業務邏輯**（無速率限制、無嘗試上限）與真實系統完全相同。

## 四、XSS 盲打平台（X1，1/1）

### 自建 callback 接收端（連接埠 8942）

```
/c?u=資料&blind=1     ★ 接收 callback
/records              JSON 記錄
/                     視覺化面板
```

### 實測的完整鏈條

```
步驟 1   POST /comment 存入含 callback 的 XSS 載荷 → HTTP 200
步驟 2   GET /comments → payload 原樣輸出（未轉義）→ True
步驟 3   模擬瀏覽器執行載荷 → 對盲打平台送出 callback
步驟 4   查盲打平台記錄 → 收到 1 筆，含 blind=1 標記 ✓
```

**盲打平台實際收到的記錄**（來自伺服器日誌）：
```json
{"ts": "2026-10-15T17:58:55", "path": "/c",
 "query": {"u": "fake-cookie-value", "ref": ".../comments", "blind": "1"},
 "ua": "Python-urllib/3.12", "ip": "127.0.0.1"}
```

### 為什麼這比一般 XSS 驗證更完整

| | 一般 XSS 驗證 | **盲打驗證** |
|---|---|---|
| 確認什麼 | payload 被原樣輸出 | payload **真的在瀏覽器執行並回傳** |
| 需要什麼 | 只看回應 | **需要接收端** |
| 證明什麼 | 可能有 XSS | **攻擊者可實際竊取資料** |

> **「需要接收端」是盲打與一般 XSS 驗證的關鍵差異。**
> 這也是為什麼課程用了整整 2 集（P39–P40）講「自建盲打平台」。

**結論**：
- **框架漏洞**：已取得真實靶場配置與官方 CVE 資料；**執行**需 Docker（本機無）。
  替代方案是用 Maven Central 下載特定版本 jar 做**靜態版本比對**。
- **雲安全**：需要真實雲帳號才能完整練習；本專案的 `ssrflab` 已模擬

## 八、三個環境限制的誠實結論

| 項目 | 判定 | 理由 |
|---|---|---|
| **帳號接管 / 短信 / 盲打** | ✅ **可完整實作** | **自己補上缺失的服務**（SMS 閘道、接收端） |
| **框架漏洞** | ⚠️ 部分 | 已取得真實配置與 CVE 資料；**執行需 Docker** |
| **雲安全** | ⚠️ 部分 | 核心機制（metadata/憑證）已模擬；**完整需雲帳號** |

> **最重要的收穫**：原本判定「需額外條件」的三項，實際上有兩項
> （帳號接管、短信、盲打）**只要自己實作缺失的服務就能完整做**。
>
> **「缺少外部服務」往往不是真正的阻礙，而是「願不願意自己實作那個服務」。**
