# 如何提升 fuzzer 的命中率：實測與反直覺發現

> 對應研究報告 **CH06 S2（工具鏈優化）** 與 **CH03**（覆蓋率引導的極限）。
>
> 本文不停留在「列出最佳實踐」，而是**實際實作、實測、並量化每一項改進的貢獻**——
> 包含一個與直覺相反的結果。

- 演練日期：2026-10-15
- 環境：Windows + LLVM-MinGW（clang 23.1.1）+ ASan + `trace-pc-guard`
- 靶場：`fuzz_target.c`（11 層巢狀條件 + 整數截斷導致的 heap overflow）

---

## 一、起點：先診斷瓶頸，而不是盲目加功能

v1 的實測數據揭露了一個警訊：

| 模式 | 迭代數 | 覆蓋率 | 結果 |
|---|---|---|---|
| guided | 2,739–7,780 | **10 / 93（10.8%）** | ✅ 找到 crash |
| blind | 500,000 | **13–14 / 93（14–15%）** | ❌ 找不到 |

**「低覆蓋的 guided 找到漏洞、高覆蓋的 blind 找不到」**——
這說明 v1 的「新穎性判準」鑑別力不足：
`basic block coverage` 只知道「這個 block 被碰過」，
不知道「是從哪條路徑進來的」，也不知道「進來了幾次」。

AFL 早就為此設計了解法。v2 採用其中四項：

| # | 改進 | 解決什麼問題 |
|---|---|---|
| 1 | **Edge coverage**（`prev→cur` 轉移） | 同一 block 從不同前驅進入 = 不同探索成果 |
| 2 | **Hit count 分桶** | 0/1 判斷遺失「迴圈深度」這種路徑訊息 |
| 3 | **字典輔助** | 盲猜 16-bit 值效率極低（1/65536） |
| 4 | **多策略 mutation** | 單一策略對不同結構的輸入適應性差 |

## 二、實作細節

### 2.1 Edge coverage（AFL 的核心）

```c
void __sanitizer_cov_trace_pc_guard(uint32_t *guard) {
    uint32_t idx = *guard;
    g_guard_flags[idx] = 1;                    /* v1：block 命中 */

    if (g_guard_hits[idx] < 0xFFFF) g_guard_hits[idx]++;  /* v2：執行次數 */

    /* v2 關鍵：記錄 (prev → cur) 的轉移 */
    uint32_t edge = ((g_prev_guard << 5) ^ (idx >> 3) ^ idx) & (EDGE_MAP - 1);
    g_edge_map[edge] = 1;
    g_prev_guard = idx;
}
```

因為 guard 已插樁在每個 basic block 開頭，**連續兩次回呼的索引就代表一條邊**。
這就是 AFL 的 edge coverage（簡化版），實測本靶場產生 **23–25 條邊**。

### 2.2 Hit count 分桶（AFL 的 CLASSIFY_COUNTS）

```c
int cov_bucket(uint32_t i) {
    uint16_t c = g_guard_hits[i];
    if (c == 0) return 0;
    if (c == 1) return 1;  if (c == 2) return 2;  if (c == 3) return 3;
    if (c < 8)   return 4;  if (c < 16)  return 5;  if (c < 32)  return 6;
    if (c < 128) return 7;  if (c < 256) return 8;
    return 9;
}
```

**新穎性判斷從「是否 0/1 變化」升級為「bucket 是否變化」**：

```c
if (b != 0 && b != global_bucket[g]) {   /* 含 0→N 與 N→M */
    global_bucket[g] = b;
    is_new = 1;
}
```

意義：同一個 block 被碰到「更多次」代表進入更深的迴圈——
那是新的程式狀態，只用 0/1 會遺漏。

### 2.3 字典輔助

把「可能有意義的位元組」集中：`0x00, 0x01, 0x0A, 0x46('F'), 0x5A('Z'), 0xC0, 0xDE, 0xFF` 等 18 個值。
理論上把搜尋空間從 256 降到 18（**約 14 倍縮減**）。

> 在實務上這個字典來自：規格文件、既有 corpus 抽取、**或 LLM 生成**。
> 這正是 CH02.2「seed 生成 / mutator 學習」能插進來的位置。

### 2.4 格式感知 mutation

```c
case 6: {   /* checksum-aware：改動標頭後自動重算，維持格式不變量 */
    dst[rnd_n(6)] = DICT[rnd_n(N_DICT)];
    uint8_t ck = 0;
    for (int k = 0; k < 6; k++) ck ^= dst[k];
    dst[8] = ck;
    break;
}
case 7: {   /* declared 欄位導向：讓 16-bit 值容易落在漏洞視窗 */
    uint16_t v = 0xC000 + (uint16_t)rnd_n(0x100);
    dst[6] = v >> 8;  dst[7] = v & 0xFF;
    break;
}
```

## 三、實測結果

### 3.1 v1 vs v2（8 組 seed，迭代上限 200,000）

| 版本 | 命中率 | 中位迭代 | 範圍 |
|---|---|---|---|
| v1（block coverage + 0/1） | 8/8 (100%) | **7,177** | 3,965 ～ 19,805 |
| **v2（edge + bucket + 字典）** | 8/8 (100%) | **591** | 23 ～ 2,293 |

**中位迭代改善：12.1 倍**（同樣 100% 命中率下，v2 平均少跑 ~12 倍）。

### 3.2 Ablation 實驗（12 組 seed，迭代上限 200,000）

| 變體 | 命中率 | 中位迭代 | 平均 | 範圍 |
|---|---|---|---|---|
| **A 完整 v2** | 12/12 | 1,008 | 1,291 | 57 ～ 3,635 |
| **B 無字典** | 12/12 | **389** | **418** | 28 ～ 1,283 |
| **C 無格式感知** | **4/12** | **50,735** | 59,404 | 21,808 ～ 130,832 |

## 四、兩個反直覺的發現（本文最有價值之處）

### 發現 1：**「格式感知」是決定成敗的唯一關鍵**

| | 命中率 | 中位迭代 |
|---|---|---|
| 有格式感知 | **12/12（100%）** | 1,008 |
| 無格式感知 | **4/12（33%）** | **50,735（慢 50 倍）** |

移除 checksum-aware 與 declared 導向後：
- 命中率從 100% 掉到 **33%**
- 中位迭代從 ~1,000 暴增到 **50,735（慢 50 倍）**

**⚠ 自檢後的修正**（見 `S2c_selfcheck.md` 與 `S2d_hitrate_instability.md`）：
用另一組 seed 重跑時，命**中率**得到 **5/8（62.5%）** 而非 33%。
更進一步的根因調查顯示，**命中率本質上是「迭代預算」的函數**：

| 迭代預算 | 累積命中率（24 組 seed） |
|---|---|
| 10,000 | 4% |
| 100,000 | 33% |
| **200,000** | **50%** ← 本實驗使用的預算 |
| 500,000 | 79% |
| 1,000,000 | 92% |

因此更精確的敘述是：

> 移除格式感知後，**中位迭代從 787 暴增至 190,726（慢 242 倍）**，
> 命中時間呈**重尾分布**（9,305 ～ 940,672，範圍 101 倍）。
> 當預算設在中位數附近（20 萬）時，命中率會在 50% 附近劇烈跳動——
> **33%、50%、62.5% 都是同一個分布的切片，不是三個矛盾的結論。**

**這驗證了 CH03 的核心論點**：當觸發條件包含「格式不變量」（如 checksum）時，
**純 mutation 需要極大量的嘗試才能穿透**。
覆蓋率只能告訴你「走到哪裡」，不能告訴你「怎麼走過去」。

### 發現 2：**字典反而讓效能變差（−2.6 倍）**

| | 中位迭代 | 平均 |
|---|---|---|
| A 完整（含字典） | 1,008 | 1,291 |
| **B 無字典** | **389** | **418** |

**移除字典，速度反而快 2.6 倍。**

**為什麼？** 合理推測：
- 字典把 mutation 限制在 18 個值內，**減少了探索的多樣性**
- 目標需要的是「精確的 0xC0XX 值」，字典中的 `0xDE`、`0xFF` 等是**無效的干擾**
- 有時候**純隨機的均勻分布反而更好**——因為它不會過度集中在錯誤的假設上

**這個發現的普適教訓**：
> **「直覺上該有幫助」的優化，必須實測。**
> 字典是 fuzzing 的標準最佳實踐，但在**這個特定的目標上**它是負面的。
> 原因不是字典本身錯，而是**我提供的字典與目標的實際需求不匹配**——
> 我猜測「FZZ 魔數很重要」，但實際上真正的關鍵是 `declared` 欄位的數值分布。

這正好對應 CH05 的論點：**「評價基準本身也可能被 gaming」**，
以及為什麼 AI 輔助 fuzzing 需要**量測**而非**相信直覺**。

## 五、提升命中率的優先順序（依實測貢獻排序）

| 優先序 | 手段 | 實測效果 |
|---|---|---|
| **1** | **格式感知 mutation**（維持不變量、導向關鍵欄位） | 命中率 33% → 100%，快 50 倍 |
| **2** | **移除過度假設的字典**（或改用真正相關的字典） | 快 2.6 倍 |
| **3** | Edge coverage + hit count 分桶 | 快 ~12 倍（v1 → v2 整體） |
| **4** | 多策略 mutation | 已含在 v2 中 |
| 5 | Corpus 最小化（AFL 的 `cmin`） | 未實作 |
| 6 | Corpus 持久化（跨 session 累積） | 未實作 |
| 7 | 平行化（多 worker）+ 定期同步 corpus | 未實作 |
| 8 | 分散式 fuzzing（多機器） | 未實作 |

### 未實作的進階手段（附原理說明）

| 手段 | 原理 | 為何有效 |
|---|---|---|
| **Corpus 最小化** | 移除「對覆蓋率無貢獻」的輸入 | 減少 corpus 重複、提升調度效率 |
| **能量分配**（AFL 的 power schedule） | 按「路徑稀有度」分配執行次數 | 把算力集中在少人走的路徑 |
| **Splice**（跨 corpus 交叉） | 組合兩個輸入的片段 | 產生既有語料中不存在的新結構 |
| **Deterministic stages** | 系統性翻轉每個位元（AFL 的 bitflip/arith/interest） | 保證基本變體都被試過 |
| **比較式引導（CmpLog）** | 記錄 `if (x == magic)` 的比較值，直接餵入 | 直接攻破「魔數比對」這種瓶頸 |
| **LLM 生成 seed / mutator** | 理解格式語意後產生合法輸入 | 對格式不變量最有效（對應 CH02.2） |

> **CmpLog 值得特別注意**：本實驗的「11 層條件」正是 CmpLog 的典型適用場景。
> 它會記錄程式中所有的比較運算（`data[0] != 0x46`），
> 然後把比較值直接寫進輸入——**這是「格式感知」的自動化版本**，
> 不需要人工提供字典。
