# S2 效能：盲注速率提升（實測 7–12 倍）

> 回答「解到 natas20 效率有點慢，有辦法提升速率嗎」。
>
> 對應研究報告 **CH06 S2**，延續 **S2d（Natas 14–19）** 與 **S2e（盲注補強）**。

- 日期：2026-10-19
- 靶場：`blindlab`（本機，含模擬網路延遲）
- **實測加速：布林盲注 7.0×、時間盲注 12.4×**
- **四種方法洩漏結果完全一致**（加速不影響正確性）

## 一、先誠實面對：哪裡慢？

回顧 natas14–19 的實際耗時：

| 關卡 | 請求數 | 單次耗時 | 總耗時 | 主因 |
|---|---|---|---|---|
| natas14 | 3 | ~1s | 3 秒 | 正常 |
| natas15 布林盲注 | ~200 | ~1s | **~3.5 分** | **序列等待** |
| natas16 命令盲注 | ~256 | ~0.7s | **~10 分** | 序列 + 大回應 |
| natas17 時間盲注 | ~192 | 1s SLEEP | **~5.4 分** | **序列 + SLEEP 太長** |
| natas18/19 掃描 | 640 | ~0.3s | 38 秒 | 已是並發 |

### 三個瓶頸

```
① 序列請求   100% 的等待時間都在「等上一個回應」
② SLEEP 太長  time-based 每次判斷固定睡 1 秒
③ 無連線重用  每次請求都重新 TCP 握手
```

### 一個額外開銷（我自己造成的）

我在 natas17 做過**三次**驗證：
1. 首次盲注（324 秒）
2. LIKE 前綴定位錯誤（~60 秒）
3. 多次測量重解（~300 秒）

**驗證是必要的**（第一次確實解錯了），但**可以更聰明**：
- 每解一個字元就立即用前綴驗證（多花 1 次請求，而非整輪重跑）
- 或用「多次測量」一次到位（每題 3 次，成本 3×，但免去重跑）

**四種方法洩漏的結果完全一致**：
```

```

### 2.3 加速來源拆解

| 手段 | 效果 | 說明 |
|---|---|---|
| **並發（8 threads）** | **7.0×** | 8 個位置同時二分；接近理論上限 8× |
| **縮短 SLEEP（1.0→0.3）** | 額外 **3.3×** | 時間判斷的固定成本降低 |
| 兩者疊加 | **12.4×** | 8 × 3.3 ≈ 26×（實際 12.4×，受伺服器處理限制） |

> **為什麼時間盲注加速更多？**
> 因為它的固定成本（SLEEP）佔比最高——
> 並發消除「等待」，縮短 SLEEP 消除「固定延遲」，兩者相乘。

## 三、可重用的加速手法（按效益排序）

### 手法 1：並發（最大效益，7×）

**核心洞察**：盲注的每個字元位置**互相獨立**——
位置 1 的解不依賴位置 2。所以可以同時解。

```python
with ThreadPoolExecutor(max_workers=8) as ex:
    futures = {ex.submit(find_char, pos): pos for pos in range(1, 33)}
```

**注意**：
- 並發數不宜過高（避免觸發限流 429）
- 建議 4–16，視平台而定
- OverTheWire 實測沒有明顯限流（但不要暴力太多）

### 手法 2：縮短 SLEEP（時間盲注專屬，3.3×）

```python
# 原本
SLEEP(1)  → 每次判斷至少 1 秒
# 優化
SLEEP(0.3) → 每次判斷 0.3 秒
```

**關鍵**：**先校準基準時間**，再設閾值：

```python
base_med = median([probe("1=2") for _ in range(3)])   # 正常
slow_med = median([probe("1=1") for _ in range(3)])   # 慢
threshold = (base_med + slow_med) / 2                  # 自適應閾值
```

**風險**：SLEEP 太小會被網路抖動誤判（這就是我 natas17 第一次解錯的原因）。
**建議**：SLEEP 0.3–0.5 秒 + 多次測量。

### 手法 3：連線重用（約 10–20%）

```python
# 用 http.client 的 keep-alive，而非每次 urllib 開新連線
conn = http.client.HTTPConnection(host, port)
conn.request("GET", path)   # 重用同一個 TCP 連線
```

### 手法 4：減少請求數（有限）

二分搜尋已是 `log2(95) ≈ 6.6` 次/字元，**接近理論下限**。

可微調：
- 若已知字元集（Natas 密碼是 `[A-Za-z0-9]` = 62 種）→ `log2(62) ≈ 6` 次
- 節省約 10%，效益不大

**不要用**「逐字元暴力」（62 次/字元）——比二分差 10 倍。

### 手法 5：避免重複驗證

```python
# 不好：整輪跑完才發現錯，重跑整輪（3 倍成本）
# 好：每解一個字元就驗證（多 1 次請求）
ch = find_char(pos)
if not verify_prefix(prefix + ch):
    ch = brute_force_char(pos)   # 只重解這一個
```

### 手法 6：能讀就別猜

如果有**任何**回饋（錯誤訊息、資料輸出），就直接讀，不要盲注：

```
B3 錯誤訊息洩漏  → 直接讀（1 次請求）
B1 布林盲注      → 二分（~200 次請求）
B2 時間盲注      → 二分 + SLEEP（~200 次 × 1 秒）
```

**先探測回饋程度，再選最便宜的手法。**

## 四、實際應用建議（Natas 場景）

### 建議參數

| 情境 | 並發 | SLEEP | 預估耗時（35 字元） |
|---|---|---|---|
| 布林盲注 | 8–16 | — | 12–25 秒 |
| 時間盲注 | 8 | 0.3–0.5s | 16–30 秒 |
| 大型掃描（640 session） | 8–16 | — | 30–40 秒 |

### 注意事項

1. **不要過度並發**：可能觸發 429 或被暫時封鎖
2. **先測限流**：用少量請求確認平台行為
3. **加退避**：遇到 429 時指數退避
4. **保留驗證**：加速後仍要驗證結果（我在 natas17 的教訓）

## 七、結論

### 三個可立即套用的加速手段

1. **並發**（最大效益）：盲注位置互相獨立 → 8 threads = 7×
2. **縮短 SLEEP**（時間盲注專屬）：1.0→0.3 秒 = 再多 3.3×
3. **連線重用**：減少握手開銷

### 兩個觀念

1. **先探測再選手法**：有回饋就別盲注（B3 直接讀 vs B2 盲注）
2. **加速不等於省驗證**：我在 natas17 的教訓——快，但必須確認正確

### 實測結論

```
布林盲注：83.0s → 11.9s  （7.0×）
時間盲注：199.5s → 16.1s （12.4×）
四種方法結果完全一致 ✓
```

**把「等」變成「同時做」，是盲注加速的核心。**
