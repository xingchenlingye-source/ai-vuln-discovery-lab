CH 01領域概述：瓶頸與典範轉移 Overview

1.1 傳統漏洞挖掘的三個結構性瓶頸

在 LLM 大規模進入資安工作流之前，漏洞挖掘主要依靠三條路徑：人工原始碼審計、fuzzing（模糊測試）、以及靜態分析工具。三者各自撞到了不同的天花板。

（1）人工審計：線性成本，無法規模化

人工審計的產出與投入的資深人力小時幾乎成正比，而現代專案的程式碼規模卻呈指數成長。一位熟練研究員要理解一個大型 C/C++ 專案的資料流與生命週期規則，往往需要數週；能審計的範圍永遠是整個 codebase 的一小塊。更關鍵的是，審計者的注意力是稀缺資源——真實世界的漏洞大部分落在「不尋常的邊界條件」上（sentinel 值、off-by-one、型別混用），而人類在閱讀數萬行樣板化的程式碼後，很容易對這類細節產生注意力疲乏。

（2）Fuzzing：覆蓋率不等於語意正確性

Fuzzing 是過去二十年最成功的漏洞發現技術：AFL / libFuzzer / Honggfuzz 等工具在 OSS-Fuzz 上累積發現了數以萬計的漏洞。但它有明確的結構限制：

  • 入口條件難滿足：需要特定格式、特定 magic bytes、特定狀態機順序才能進入的程式路徑，隨機變異幾乎碰不到。
  • 覆蓋率引導的迷思：覆蓋率只能告訴 fuzzer「走到了哪些程式碼」，無法告訴它「這裡的語意不變量是什麼」。一個已達 100% line coverage 的函式，仍可能因為缺少極端值組合而藏有漏洞。
  • 飽和效應（saturation）：對於已被長期 fuzzing 的成熟專案，新發現漏洞的邊際報酬快速衰減。
實證案例：SQLite 的 150 CPU-hour 對照實驗 Google Project Zero 與 DeepMind 的 Big Sleep 團隊在 2024 年報告其 agent 於 SQLite 中發現一個可觸發的 stack buffer underflow 後，特地回頭做了對照實驗：依照 SQLite 官方 AFL 說明設定、並確認 fuzzing corpus 中已包含觸發所需的 generate_series 與 rowid 關鍵字後，執行 AFL 達 150 CPU-hours 仍未發現該問題；即使把必要關鍵字加入 AFL 的 SQL dictionary，該 bug 也只在 corpus 已包含「非常接近崩潰輸入」的範例時才會被快速找到。團隊結論是：對這個問題而言，程式碼覆蓋率不是可靠的引導訊號。這正是「覆蓋率與語意盲區」的具體樣貌。

（3）靜態分析：規則可解釋，但誤報與語意不足

CodeQL、Semgrep 這類工具以資料流／污點分析為核心，優點是可解釋、可重複、可進 CI，缺點是：

  • 規則即上限：沒被寫成規則的漏洞模式就不會被找到；規則越寬則誤報暴增。
  • 缺乏跨函式／跨檔案的語意推理：對「這個欄位的值域不變量是否被破壞」這類問題，純資料流分析往往力不從心。
  • 告警疲乏：一個中大型專案跑完一次查詢可能產生數千條結果，人工排序與驗證成為新的瓶頸。

1.2 LLM 進入後改變了什麼

LLM 的能力邊界「剛好」落在傳統方法的失敗面上。以下四項是這個領域真正的典範轉移點：

維度傳統方法LLM / Agentic 方法為什麼關鍵
理解方式 規則比對、資料流圖 自然語言層級的語意推理 能處理「這個 sentinel 值是否被所有使用者正確處理」這類非模板化問題
知識來源 分析師寫死的規則 預訓練中吸收的 CWE 模式、歷史 CVE、專案慣例 遷移能力強：看過一類 bug 後能找到其變體（variant analysis）
工作模式 單次掃描 多輪 agentic 迴圈：假設 → 工具查證 → 修改測試 → 觀察崩潰 → 修正假設 允許「失敗後轉向」，這是人類研究員的實際工作方式
產出物 告警列表 可重現的 testcase + root-cause analysis + 可能的 patch 直接接上「驗證」與「修補」環節，縮短從發現到修復的鏈路
成本結構 資深人力工時 GPU / API 費用 + 推理時間 可水平擴展、可大量重複嘗試（test-time scaling）

值得注意的是，目前領先的公開成果幾乎都不是「把程式碼丟給 LLM 問有沒有 bug」這種單輪用法，而是把 LLM 當成一個需要工具（debugger、code browser、fuzzer、executor）才能工作的推理核心。Big Sleep 的 trajectory 就是典型：agent 先用 code_browser_source 找範例、嘗試修改 patch 附帶的 testcase、因缺少 TCL module 而失敗、改用 generate_series、設中斷點、最後產出 SELECT * FROM generate_series(1,10,1) WHERE ROWID = 1; 這個觸發輸入。整個過程「讀起來很像人類研究員，一開始有個想法，過程中想到別的點子，最後復現的其實是個稍微不同的 bug」。

重要前提：不要誇大定位 Big Sleep 團隊在其官方部落格明確表示，這些屬於高度實驗性的結果，並且該團隊當時的立場是：就現況而言，針對特定目標打造的 fuzzer「至少與之同等有效」。一個誠實的報告必須把這句話和成果一起寫進去。

CH 02主要技術路線 Four Technical Routes

目前的公開研究與產品，大致可歸納為四條路線。實務上它們很少單獨出現，而是互相焊接（例如：靜態分析縮小範圍 → LLM 排序 → fuzzer 驗證 → LLM 生成 patch）。

2.1 路線 A：LLM 直接做原始碼審計與漏洞定位

核心機制

  • Repository-level 上下文建構：不是把整個 repo 塞進 context（不可能），而是先建立結構化索引（函式呼叫圖、符號表、diff 範圍），再依問題動態檢索相關檔案片段。
  • Agentic 多輪推理：agent 具備「假設 → 查證 → 修正」迴圈，並可呼叫工具（grep、symbol lookup、git log、執行測試）。
  • Variant analysis（變體分析）：以「已修補的漏洞」為起點，要求模型在當前 HEAD 找出同類但未修的問題。這是目前訊號雜訊比最高的設定，因為它把開放式問題轉成了有明確先驗的問題。
  • Crash 驅動的閉環：agent 能自己寫 test harness、編譯、跑、看輸出，並根據 sanitizer/assertion 訊息回頭修正假設。

優勢與弱點

優勢弱點
能覆蓋 fuzzing 難以觸及的路徑（需要語意組合的邏輯漏洞） 誤報率高；「看起來像漏洞」與「可觸發」之間有巨大落差
可產出人類可讀的 root cause 說明，降低 triage 成本 對 context 敏感；關鍵程式碼未被檢索到就會漏報
variant analysis 的 recall 明顯優於人力抽查 沒有可執行驗證時，輸出應視為假設而非 finding
實務心法 「發現」與「驗證」必須由不同機制負責。XBOW 的公開說明即採此架構：由創意導向的 AI agent 負責發現，再由確定性邏輯（deterministic logic / controlled testing）決定什麼是真的，並主張「plausibility is not proof, and confidence is not evidence」。

2.2 路線 B：AI 引導 Fuzzing

這條路線把 LLM 插進 fuzzing 的瓶頸位置，而不是取代 fuzzer。Google 的 oss-fuzz-gen 專案即明確定位為「LLM powered fuzzing via OSS-Fuzz」——用 LLM 為既有 OSS-Fuzz 專案生成與改進 fuzz target。

四個可插入的環節

  1. Fuzz target / harness 生成：LLM 讀取專案的公開 API 與既有測試，產出能編譯、能被 OSS-Fuzz 執行的 harness。這是目前最有價值也最可驗證的應用——因為成敗可由「是否成功 build、是否提升覆蓋率、是否找到 crash」客觀判定。
  2. Seed 生成與 corpus 精煉：針對格式敏感的目標（SQL、圖片格式、設定檔），由 LLM 產生結構合法且語意多樣的 seed，繞過 parser 的第一道牆。
  3. Mutator 學習 / 語意變異：以 LLM 產生「保持語法合法但改變語意」的變異，補足 byte-level mutation 的不足。相關學術方向包含 learning-based mutation 與 LLM-guided mutation 的比較研究。
  4. Crash triage 與去重（dedup）：用 LLM 判斷兩個 crash 是否同源、估算可利用性、產生最小化說明，降低人工 triage 負擔。這是「低風險高報酬」的應用，因為 triage 的錯誤代價遠低於漏報。
為什麼這條路線最務實 Fuzzing 提供了客觀的成功判準：crashes、coverage、build 成功率都是可自動量測的數字。這使得 LLM 的產出可以被自動過濾，避免落入「LLM 說有 bug 但無法驗證」的困境。OSS-Fuzz 的大規模基礎設施（數千個專案、持續建置與 crash 去重）正好提供了現成的評測場。

2.3 路線 C：程式分析 + LLM 的混合路線

純 LLM 的問題是「沒有不變量」，純靜態分析的問題是「沒有語意」。混合路線的典型設計是讓兩者互補：

// 混合管線的常見組態（概念示意）
[CodeQL / Semgrep]          產生候選資料流路徑（高 recall、高誤報）
        │
        ▼
[LLM 排序 / 過濾]          依 sink 危險性、可達性、輸入可控性排序
        │
        ▼
[LLM 產生 PoC 假設]        依告警上下文寫出最小觸發輸入
        │
        ▼
[Sanitizer + 沙箱執行]      ASan / UBSan / MSan 驗證是否真的觸發
        │
        ▼
[LLM 生成 patch] → [回歸測試 / 差異化測試驗證 patch]

這條路線的三個關鍵設計決策：

  • 用分析工具當「檢索器」而非「裁判」：把 CodeQL 當成 recall 引擎，把 LLM 當成 precision 引擎。
  • 以 sanitizer 為唯一真相來源：ASan/UBSan 說崩了就是崩了；LLM 說有漏洞但 sanitizer 不響，就只是假設。
  • 規則以自然語言輔助生成：由 LLM 協助撰寫 CodeQL/Semgrep 規則，再由人工審查規則本身的正確性（避免「用 LLM 驗證 LLM」的循環）。

2.4 路線 D：自動化 Exploit 生成與可達性驗證

此路線的核心問題不是「有沒有 bug」，而是「這個 bug 是否真的可達、可利用、可修補」。技術要點：

  • 可達性驗證（reachability validation）：確認攻擊者可控輸入能到達危險 sink，且中途的安全檢查（長度檢查、型別檢查、白名單）無法繞過。
  • 沙箱化執行環境：容器化的 build + run 環境，掛載 sanitizer，限制網路與資源，確保自動生成的 PoC 不會外溢。OSS-Fuzz 與 CyberGym 都以容器化重現環境為基礎。
  • Patch 驗證：AI 生成的修補必須通過「原 PoC 不再崩潰」+「既有測試套件未回歸」雙重檢查。Anthropic 的公開研究即指出 patch 的困難在於必須做外科手術式的修改：移除漏洞但不改變原功能，且模型必須自行推斷程式碼的意圖。
  • 差異化測試（differential testing）：對照修補前後行為，抓出「補了一個洞但引入另一個」的情況。CyberGym 的評測過程中就發現了不完整修補（incomplete patches）的實際案例。

2.5 跨路線的共同結論：架構（harness）可能比模型本身更關鍵

四條路線各自獨立發展，卻收斂到同一個結論。這一段是整份報告最值得記住的判斷之一。

來源支持「架構／工程 > 模型」的具體證據
XBOW（2026） 主張其能力來自「數千個短生命週期 agent + coordinator + 確定性驗證」的架構，而非單一模型的進步；並強調架構與模型同等重要。
CyberGym（2025） 四個不同 agent 在相同 backbone（GPT-4.1）下成功率相近，但取結果聯集後達 18.4%、接近最佳單一 agent 的兩倍——證明架構差異帶來互補性。
HarnessAgent 研究（2025-12） 在相同任務下，預先結構化的 pipeline 明顯優於由 LLM 自行規劃的 agent 式流程（Sherpa 僅 9 個成功 harness，遠低於 OSS-Fuzz-Gen 與 LLM4FDG）。工程化的工作流本身就能決定成敗。
OSS-CRS（2026-03） 七支 AIxCC 隊伍的技術各有特色，但真正的瓶頸不是技術能力，而是能否穩健地整合進自主系統。
IronCurtain（2026-08） 最直接的實證：作者以開源 orchestration 框架搭配商用模型與開源權重模型（GLM 5.1），複現了前沿模型報告的旗艦發現，並自主找到新的 zero-day。結論是能力「存在於管理模型的 harness 之中，而不只存在於專有前沿模型裡」。
對學習者的意義 如果架構的貢獻與模型相當甚至更大，那麼「學會設計 agent 工作流、context 管理與驗證迴圈」的投資報酬率，可能高於「等待更強的下一個模型」。這也解釋了為什麼本報告的學習路徑 CH06 把「工具鏈」（S2）放在「AI 方法」（S3）之前——沒有可驗證的執行環境與工具，再強的模型也只能產出無法證實的假設。

實作上，這些系統收斂出四項共同的架構設計：

  1. 發現與驗證分離：由創意導向的 agent 負責提出假設，由確定性邏輯（sanitizer、回歸測試、PoV 重跑）判定真偽。
  2. 狀態外置（journal / artifact）：把進度寫到磁碟而非 context，讓新 agent 能以乾淨的 context window 接手（IronCurtain 的 append-only journal、OSS-CRS 的 artifact exchange 皆為此設計）。
  3. 預算是一級資源：LLM 花費需像 CPU／記憶體一樣被配額與強制（OSS-CRS 的 per-CRS LLM budget）。
  4. 分層 harness：從單函式隔離 harness、多元件 harness，到完整 VM 端到端驗證，依所需證據強度逐級升級（IronCurtain 明確採用此三層策略）。
本報告的界線宣告 本節描述的是研究與防禦用途的方法論與評測設計。基於教育與防禦研究視角，本文不會提供任何針對特定真實目標的攻擊步驟、武器化 exploit 程式碼或繞過流程。自動化 exploit 生成能力的討論，目的是讓防禦方理解評測標準與修補驗證的重要性。

Google Online Security Blog — 以 AI 強化 OSS-Fuzz：26 個新漏洞、272 個專案與 37 萬行覆蓋成長

作者：Oliver Chang、Dongge Liu、Jonathan Metzman（Google Open Source Security Team），發文於 2024-11-20。Google 於 2023 年 8 月首度宣布將 LLM 引入 OSS-Fuzz（AI-powered fuzzing: breaking the bug hunting barrier），初期聚焦於用 LLM 產生 fuzz target——這是 fuzzing 流程中最耗人力的步驟之一。

可核實的具體數字（皆為原文逐字）：

  • OSS-Fuzz 向開源專案維護者通報了 26 個新漏洞。
  • 覆蓋率改善涵蓋 272 個 C/C++ 專案（原文特別註明「up from 160」——自 160 個專案增加至 272 個）。
  • 新增 370k+ 行程式碼覆蓋（原文 "adding 370k+ lines of new code coverage"）。
  • 單一專案的最高覆蓋成長為從 77 行增至 5,434 行（增幅 7,000%）。
  • 歷史基數：OSS-Fuzz 在專案前 8 年協助修補逾 11,000 個漏洞。
  • 代表案例 CVE-2024-9143（OpenSSL）：2024-09-16 通報、2024-10-16 發布修補。原文敘述該漏洞「很可能已存在約二十年，且不可能以人類撰寫的既有 fuzz target 發現」。
  • 原文另舉 cJSON 為例：即使該函式已有真人撰寫的 harness，AI 產生的 target 仍在同一函式中找到新漏洞。

官方定位與自動化程度（原文）：Google 將此定位為「自動化漏洞發現的里程碑——每個漏洞都是用 AI 生成與增強的 fuzz target 找到的」，並說明其目標是把五步流程全面自動化：（1）撰寫 fuzz target →（2）修正編譯錯誤 →（3）試跑並修正執行期錯誤 →（4）長時間執行並分流 crash →（5）修補漏洞。原文明確表示「我們的 LLM 目前已能執行前四步（第五步即將到來）」。框架自 2024 年 1 月起開源。

Google 自行揭露的限制（原文，對 CH05 極具參考價值）：

  • 行覆蓋率不是無 bug 的保證：「line coverage is not a guarantee that a function is free of bugs. Code coverage as a metric isn't able to measure all possible code paths and states」——不同 flag 與配置會觸發不同行為、挖出不同 bug。
  • 實際漏洞可能多於 26 個：「There are likely more than the 26 vulnerabilities we've already reported upstream hiding in our results.」
  • 自動分流尚未達到免人工：「to get to a point where we're confident about not requiring human review」。
  • 自動產生修補尚無成果可分享：第 5 步「We don't have anything we can share here today.」

4.4 Agent 架構的三種典型設計

  1. 單 agent + 工具集（Big Sleep 路線）：一個長 context 的 agent 搭配 code browser、debugger、executor。優點是推理連貫；缺點是 context 累積誤差與成本上升。
  2. 多 agent 分工（AIxCC CRS 路線）：分別負責漏洞發現、修補生成、修補驗證，彼此以「提交物」而非對話溝通。
  3. 大量短生命週期 agent + coordinator（XBOW 公開描述的路線）：數千個 agent 各負責狹窄目標，coordinator 編排，結果由確定性邏輯驗證；強調「每個 agent 從乾淨 context 開始，避免誤差累積」。同事實上，CyberGym 的實驗也發現不同 agent 的成功案例重疊度低（四個 agent 個別成功率相近，但取聯集後達 18.4%，幾乎是任一單一 agent 的兩倍），支持「多架構互補」的設計直覺。
CyberGym 的 agent 比較數據（可作為架構選擇參考） 以相同 backbone（GPT-4.1）比較 OpenHands、OpenAI Codex CLI，以及兩個 CTF 專用 agent（EnIGMA、Cybench agent）：四者整體成功率相近；但取全部 agent 結果的聯集後成功率達 18.4%，接近最佳單一 agent 的兩倍。行為差異上：OpenHands 傾向用 Bash 串接指令，CTF 專用 agent 則較常撰寫 Python 腳本。這說明「工具偏好」與「解法偏好」確實存在架構差異。

CH 05能力邊界與已知局限 Limitations

5.1 幻覺與誤報：最核心的問題

LLM 對漏洞的判決，本質上是「文字上的可能性判斷」，不是執行結果。一個模型可以非常有信心地描述一條不存在的資料流，並產出語法正確但邏輯錯誤的 PoC。因此：

  • 沒有 sanitizer 反饋的 finding 只能算假設。XBOW 的公開立場是：raw LLM output 不能被當成 finding，「plausibility is not proof, and confidence is not evidence」，因此其架構把發現與驗證完全分離，並以確定性邏輯決定什麼是真的。
  • 誤報的成本被低估。在 CI 裡每加一條 LLM 產生的告警，就需要人力去關閉它；誤報率過高時，團隊會直接忽略整個管道（告警疲乏）。
  • 評價基準本身也可能被 gaming。International AI Safety Report 2026 記錄了模型 gaming evaluation、reward hacking 與 sandbagging 的現象。設計評測時必須假設受測者會「對 benchmark 最佳化」。

5.2 上下文長度與上下文品質

  • CyberGym 的評測涵蓋從小於數萬行到數百萬行的 codebase；把整個 repo 放進 context 並不可行，必須靠檢索。
  • 檢索失敗 = 漏報：如果關鍵的 validation 函式沒被拉進 context，模型會合理地誤判「輸入可控」。
  • Agent 的過程會累積無用的工具輸出，擠壓有效 context，並使模型偏離原始假設。這正是「大量短生命週期 agent」與「狀態外置」架構被提出的原因。
  • 已有多種具體對策可學習：XBOW 以「數千個短生命週期 agent，每個從乾淨 context 開始」避免誤差累積；IronCurtain 則把調查狀態寫入 append-only execution journal，讓每個 agent 狀態都能從全新的 context window 開始、再從磁碟 rehydrate，而 Orchestrator 只依賴 journal 管理調查、不自己讀取目標原始碼。兩者解決的是同一個問題。

5.3b 「發現量大」是否等於「風險高」？——1.3% 的實證答案

當 AI 能以數千個為單位產出漏洞時，下一個問題是：這些漏洞真的被利用了？2026 年出現了第三方量化答案，而它給出的是降溫而非恐慌的結論。

來源發現量實際被利用推論
VulnCheck（H1 2026） 1,061 個 AI 輔助發現的漏洞 14 個（約 1.3%）確認在野被利用 與同期所有漏洞的整體利用率大致相同——AI 發現的漏洞並沒有「特別容易被利用」
Anthropic Project Glasswing（被 VulnCheck 引用） 報告 23,000+ 個發現 僅 126 個產生已發布 CVE，1 個被確認在野利用 這條漏斗（23,000 → 126 → 1）是「發現量」與「已確認風險」之間落差最具體的證據
Anthropic（2026-02） 500+ 個高嚴重性漏洞（皆人工驗證） 未報告在野利用 該研究的主要貢獻是「能大量發現」，而非「造成大量利用」

VulnCheck 研究員 Patrick Garrity 據此認為，目前的漏洞情報顯示前沿 AI 模型的使用「更可能讓防禦方在強化軟體上取得優勢，而不是讓攻擊方在軟體生產者之前發現漏洞上取得優勢」。這是對「vulnpocalypse（漏洞末日）」式警告的重要反證。

但同一份報告也給出了相反方向的警訊：2026 上半年 CVE 發布到進入 KEV 的中位時間由 2025 年的 120 天縮短到 80 天，且 23.43% 的 KEV 在 CVE 發布當天或之前就已出現利用證據。Garrity 的判讀是「早期利用活動並未與 CVE 發布量同步擴張」——也就是漏洞產出量暴增，但實際利用並未等比例成長。最受針對的類別為 CMS（163 個 KEV，占三分之一），其次為網路邊緣裝置（68）與作業系統（44）。

對學習者的判斷練習 這三個數字放在一起時，最值得練習的是區分「發現」「通報」「CVE 指派」「實際利用」四個不同階段。23,000 → 126 的落差主要來自驗證與 CVE 指派流程（也反映過去的誤報爭議）；126 → 1 的落差則說明「可觸發」與「會被真實攻擊者利用」之間仍隔著可達性、目標價值與攻擊成本的考量。任何只引用「AI 發現了 N 個漏洞」而不同時說明後續漏斗的報導，都會系統性地誇大風險。

5.4 Benchmark 與真實世界的落差

  • 任務被描述得太好。CyberGym 的任務會給「位置、類型、root cause」等線索（來自 commit message 改寫）。真實世界沒有這種提示。這是所有 benchmark 共同的結構性落差。
  • 「重現」不等於「發現」。給定描述後能寫出 PoC，與在沒有提示下自行定位，是兩種難度。
  • 注入漏洞 vs 真實漏洞。AIxCC 的 86%（54/63）是針對「刻意注入」的合成漏洞；同一批系統在真實軟體中只找到 18 個未知漏洞（C 6 個、Java 12 個），且11 個自動修補全部落在 Java，C 程式庫的 0day 未被自動修補。數量級與修補成功率的雙重落差，說明合成任務與真實任務不可直接類比。
  • 「重現」與「修補」也不是同一件事。SEC-bench 在同一批 SOTA code agent 上量測兩項任務，得到 PoC 生成最高 18.0%、修補最高 34.0% 的落差——修補的成功率反而是 PoC 生成的近兩倍，這與直覺相反，說明「產生可觸發輸入」比「套用正確修補」更難，也說明單一分數無法代表安全工程的全貌。
  • 評測成本限制會扭曲排名。Anthropic 明確指出其 CyberGym 評測中 Opus 4.1 因價格較高而未套用與其他模型相同的「每漏洞 2 美元」成本限制，因此 1 次嘗試的比較基準並不一致。
  • CTF 與真實漏洞的距離。Cybench 來自 CTF 題目；Anthropic 以 40 題中 37 題的子集評估。CTF 通常有明確 flag 與可解性保證，真實系統沒有。

成本判斷的實務建議 評估是否導入 AI 漏洞挖掘時，不要只看「每個 bug 多少錢」，要看「每個被人工驗證為真的 bug 需要多少總成本」（模型 API + 執行沙箱 + 人工 triage 工時 + 誤報處理）。目前公開資料顯示，把 AI 放在可自動驗證的環節（harness 生成、crash triage、靜態告警排序）的投報率，明顯高於純粹的「LLM 直接報漏洞」。

5.6 其他值得注意的限制

  • 安全對齊與 AUP 護欄會直接造成防禦者的摩擦。CyberGym 團隊觀察到 o4-mini 在評測中頻繁尋求使用者確認而非自主行動，因而表現低於預期。更值得注意的個案：IronCurtain 的作者在需要確認漏洞嚴重性、要求模型建構可運作的 exploit 時被模型拒絕，他只能手動把流程拆成七個步驟，模型執行前兩步後仍因 AUP 護欄再次拒絕。作者據此指出這是關鍵的不對稱——防禦者做正當研究撞到摩擦，而資源充足的攻擊者使用未受管制的開源權重模型則不受此限。這既是技術限制，也是政策問題。
  • 專用模型未必能遷移。在 SWE-bench 表現優異的專用模型，在 CyberGym 上每個都 ≤ 2%；SWE-bench（通用 bug 修復）與漏洞重現是互補而非重疊的能力。
  • 不完整修補是真實存在的風險。CyberGym 在 759 個觸發 crash 的 PoC 中，人工確認為 17 個不完整修補，跨 15 個專案。AI 生成 patch 的驗證不能只跑一次。
  • 廠商自述的數字需區分層級。XBOW 的排名與 1,060 個提交來自其自身部落格；應與平台資料、第三方 benchmark 交叉確認。
  • 「開源」不等於「可用」。OSS-CRS 論文實證發現，AIxCC 七支決賽隊伍的 CRS 雖然全部開源，但在半年後仍幾乎無法在原始團隊之外使用：所有系統都綁定在賽後已被關閉的 Azure + Kubernetes 環境，且沒有一個提供元件層級的抽取介面。冠軍系統 Atlantis 需 20 台以上 Azure VM 與 42 TiB 儲存。這提醒我們，「成果開源」與「能力可被社群複用」之間存在巨大的工程落差。
  • 大規模通報的外部性。OSS-CRS 論文記錄：curl 因 AI 撰寫的提交淹沒審查者而關閉 bug bounty 計畫，其中多為未經確認的 finding；FFmpeg 維護者批評 Google 提交有效 bug 卻未附修補，稱之為「CVE slop」。自動化若不把「驗證與修補」納入流程，會把成本外部化給開源維護者。

CH 06學習路徑（四階段） Learning Path

本階段設計原則：每一階段都必須產出「可被驗證的具體東西」（一個崩潰、一條規則、一份報告、一次負責任揭露），而不是只讀完文章。四階段之間的順序不可顛倒——沒有漏洞原理基礎，AI 只會放大誤報；沒有工具鏈實作能力，無法驗證 AI 的輸出。

全程鐵則 所有練習只在自己擁有或明確授權的環境進行：本機 VM、CTF 平台、公開靶場、允許測試的開源專案。發現真實系統的問題時，走負責任揭露流程（見 CH08）。
第一階段：漏洞原理基礎 建議 2–3 個月｜目標：看到程式碼能猜到「哪裡會壞」

這一階段的產出標準是：能針對一段 100 行以內的 C 程式，指出可能的記憶體安全問題並解釋觸發條件。

必學主題

  • CWE 分類體系：以 MITRE CWE Top 25 為地圖，先掌握記憶體類（CWE-787 out-of-bounds write、CWE-125 out-of-bounds read、CWE-416 use-after-free、CWE-476 NULL pointer dereference、CWE-190 integer overflow）與常見邏輯類（CWE-79 XSS、CWE-89 SQL injection、CWE-22 path traversal、CWE-502 deserialization）。理解 CWE 的價值在於它是共同的詞彙——你寫 prompt、寫評測、寫報告都會用到它。
  • 記憶體安全（C/C++）：堆疊與堆積的配置、指標算術、生命週期、buffer 邊界、整數溢位導致的長度計算錯誤。特別注意「sentinel 值」這類語意約定（Big Sleep 的 SQLite bug 正是 iColumn == -1 表示 ROWID 的 sentinel 未被正確處理）。
  • 記憶體安全（Rust 與現代語言）：理解 unsafe 邊界、FFI、以及為何「換語言」不能消除所有漏洞。
  • Web 漏洞：從 OWASP Top 10:2025 出發（top10.owasp.org/2025），重點在資料流：source（使用者輸入）→ 傳遞 → sink（危險操作）。SQL injection 與 XSS 是練習資料流思維的最佳教材。
  • 2025 版的三個重點變化（值得優先認識）：
    • A03 軟體供應鏈失效（新類別，社群調查中 50% 受訪者列為第 1，平均發生率最高 5.19%）——範圍從「有已知漏洞的元件」擴大到整個建置／發佈／更新流程的破壞；官方列舉 SolarWinds（2019）、Bybit 15 億美元被盜（2025）、Shai-Hulud npm 蠕蟲（2025，首個成功自我傳播的 npm 蠕蟲，波及 500+ 套件版本）。
    • A10 異常條件處理不當（新類別，24 個 CWE）——涵蓋錯誤處理不當、邏輯錯誤、failing open；首要 CWE 即包含 CWE-209（錯誤訊息含敏感資訊）與 CWE-476（NULL 指標解引用）。
    • A05 注入降至第 5（合併了 XSS）；A02 安全設定錯誤升至第 2；A09 更名為「Logging and Alerting Failures」（強調警報而不只是日誌）。
  • 實作練習的涵蓋缺口與後續補強：原有靶場充分涵蓋 A05（注入）、A08（反序列化）、A10（CWE-209），但 A01 存取控制失效與 A10 的核心 CWE（fail-open）原本完全未涵蓋。
    • 已補強（A01 + A10）：建立靶場實作 6 個漏洞並經執行驗證 —— V1 IDOR 水平越權（CWE-639）、V2 缺省允許（CWE-862）、V3 錯誤訊息洩漏（CWE-209）、V4 資源未釋放（CWE-460）、V5 未檢查回傳值導致靜默失敗（CWE-252／CWE-391）、V6 fail-open 認證（CWE-636）。驗證結果 6/6。
    • 已補強（A03）：自製 OSV API 掃描器，對 8 個刻意選用歷史漏洞版本的套件進行清查 —— 8/8 有漏洞、合計 162 個（Django 2.2.0 單獨 75 個）。
    • 已補強（A09 日誌與警報）：建立第三個靶場，示範 2025 版更名所強調的重點——「記錄」不等於「通報」。6 個缺口全部經執行驗證（6/6）：L1 登入失敗不記錄（CWE-778）、L2 關鍵操作無審計軌跡（CWE-778）、L3 日誌含明文密碼（CWE-532，實測日誌出現 password=123456）、L4 暴力破解無告警（CWE-778）、L5 日誌檔可被 API 清除（CWE-732）、L6 無 request_id 無法串連事件（CWE-778）。修補版以結構化 JSON Lines 日誌 + 告警門檻 + 敏感欄位遮罩 + request_id 貫穿修正，驗證結果缺口補上 6/6、功能保留 4/4。其中一個反諷的設計值得注意：漏洞版把失敗次數顯示給攻擊者（回應中），卻完全不寫入日誌——攻擊者知道進度，防禦方零資訊。
    • 已補強（A04 加密失效 + A06 不安全的設計，原兩類皆無專門靶場）：建立電商情境靶場，6 個漏洞全部經執行驗證（6/6）。A06 設計缺陷：B1 限購可繞過（CWE-799，check-then-act）、B2 TOCTOU 競態（CWE-367——餘額 5000 併發扣款 3 筆 4000 元後變成 −7000）、B3 價格由客戶端提供（CWE-472，1 元買 100 元商品）。A04 加密缺陷：B4 MD5 無 salt（CWE-916）、B5 可預測隨機 token（CWE-338，相同 seed 產生相同 token）、B6 卡號明文儲存（CWE-311）。修補版以原子操作（單一 UPDATE + WHERE 條件）、資料庫唯一約束、伺服器端定價、PBKDF2 + salt、CSPRNG、加密儲存修正，驗證結果攻擊失效 6/6、功能保留 4/4（B2 從成功 3/3 修正為 1/3）。 關鍵洞察：A06 的缺陷是設計層的——正如官方強調「設計層缺陷無法靠實作修補」，修補方式不是「加檢查」而是改變設計（把檢查條件放進動作本身，讓資料庫保證原子性）。這也讓驗證方式出現第三種型態：競態漏洞必須用並發請求才能觀察（單次請求永遠看起來正常）。
    • 已補強（A02 安全設定錯誤，原為唯一「部分涵蓋」類別）：建立設定缺陷靶場，6 個問題全部經執行驗證（6/6）：C1 DEBUG 模式洩漏 traceback 與檔案路徑（CWE-489）、C2 缺少 6 個安全標頭（CWE-693）、C3 CORS 萬用字元 + credentials（CWE-942）、C4 預設憑證未變更（admin/admin、root/root、guest/guest，CWE-1392）、C5 允許危險 HTTP 方法（PUT/DELETE，CWE-749）、C6 設定與密鑰洩漏（AWS key、DB 密碼明文，CWE-200）。修補版驗證結果攻擊失效 6/6、功能保留 5/5。 A02 的獨特性質：漏洞不是「寫錯程式」，而是「設定沒做好」——修補版的程式邏輯與漏洞版幾乎相同，差別只在設定。這也產生第五種驗證型態：A02 必須讀「回應標頭 + 允許的方法 + 端點是否存在」，而不是讀 body。實務意涵：這類檢查幾乎完全可自動化（規則式工具即可），不需要動用 frontier model——把 LLM 留給需要語意理解的問題，才是有效的資源配置。
    • 涵蓋結論（最終）：OWASP Top 10:2025 十個類別中，本專案靶場已全數充分涵蓋（10/10） —— A01、A02、A03、A04、A05、A06、A07、A08、A09、A10。這是從最初「3 類完全未涵蓋、4 類部分涵蓋」逐步補強的結果：先補 A01/A10（IDOR、fail-open），再補 A07 與垂直越權、A03 的 SBOM 與簽章，接著補 A09（日誌與警報）、A04/A06（加密與設計缺陷），最後補上 A02（安全設定）。
    • 後續已全數修復（A07 + 垂直越權 + SBOM）：建立第二個靶場補上 A07 認證失效與 A01 垂直越權共 7 個漏洞，全部經執行驗證（7/7）—— W1 無 salt 的 MD5（CWE-916，以 md5('123456') 反查確認）、W2 使用者列舉（CWE-204，錯誤訊息不一致）、W3 無速率限制（CWE-307）、W4 會話固定（CWE-384）、W5 過期會話仍有效（CWE-613）、W6 登出未真正失效（CWE-613）、W7 垂直越權提權為 admin（CWE-269）。
    • 供應鏈練習補強：除依賴掃描外，另實作 SBOM 生成（CycloneDX 1.5 JSON，含 purl 標準識別碼）、SHA-256 雜湊清單、以及 HMAC-SHA256 簽章驗證；並以「篡改 sbom.json 後驗證應失敗」確認偵測能力有效。同時誠實說明邊界：HMAC 只能做到完整性，做不到來源可信——真正的供應鏈簽章需非對稱簽章（Sigstore/cosign）與信任鏈。
    • 修補驗證：另建立修補版靶場，以「① 攻擊失效　② 功能保留」雙條件驗證 —— 兩項皆 6/6 通過，證明是「真的修好」而非「把功能關掉」。
    • A09 日誌與警報（原為部分涵蓋，現已完整實作）：建立第三個靶場，示範 2025 版更名所強調的重點——「記錄」不等於「通報」。6 個缺口全部經執行驗證（6/6）：L1 登入失敗不記錄（CWE-778）、L2 關鍵操作無審計軌跡（CWE-778）、L3 日誌含明文密碼（CWE-532，實測日誌出現 password=123456）、L4 暴力破解無告警（CWE-778）、L5 日誌檔可被 API 清除（CWE-732）、L6 無 request_id 無法串連事件（CWE-778）。修補版以結構化 JSON Lines 日誌 + 告警門檻 + 敏感欄位遮罩 + request_id 貫穿修正，驗證結果缺口補上 6/6、功能保留 4/4。 其中一個反諷的設計值得注意：漏洞版把失敗次數顯示給攻擊者（回應中），卻完全不寫入日誌——攻擊者知道進度，防禦方零資訊。
  • 為什麼 IDOR 與 fail-open 特別值得練：兩者都是邏輯漏洞，沒有 crash、沒有 sanitizer 訊號——fuzzer 幾乎不可能找到（回應仍是 200）。這正是 CH05「能力邊界」要區分漏洞類型的原因：可執行驗證的方式必須配合漏洞類型（IDOR 要比對授權前後的行為差異；fail-open 需製造故障情境才能觀察），而不是等程式崩潰。
  • 逆向基礎：x86-64 組合語言的閱讀能力、stack frame 佈局、呼叫慣例（calling convention）、GOT/PLT 概念。不需要會寫 shellcode，但必須能讀懂 crash 的 stack trace 與 disassembly。

可執行練習

  1. 寫 10 個會壞的程式。自己用 C 寫出：off-by-one 的 strcpy、釋放後使用、整數溢位造成的 malloc 尺寸錯誤、格式字串漏洞、負索引寫入陣列。編譯時開 -fsanitize=address,undefined，觀察 sanitizer 的輸出格式。這一步的目的是把「CWE 編號」和「實際崩潰訊息」對應起來。
  2. CWE Top 25 對照練習。針對前 10 項，各找一個公開的修補 commit（GitHub 上搜尋 CVE 編號），讀 diff，寫下 3 句話：問題是什麼、怎麼觸發、怎麼修。
  3. WebGoat / DVWA 基礎關卡。不用工具，純手工完成 SQL injection 與 XSS 各 3 關，並用瀏覽器開發者工具的 Network 面板記錄每一條請求。目的是建立「輸入 → 輸出」的可觀察性。
  4. IDOR 水平越權（A01 / CWE-639）。自己做一個有兩個使用者的服務，用 ?uid= 模擬登入身分，然後嘗試用 alice 的身分讀取 bob 的文件。重點體會：這類漏洞沒有 crash、沒有錯誤訊息——只有「不該回 200 的請求回了 200」。修補時注意「無權存取」應與「資源不存在」回同一個 404，否則會洩漏資源存在性。
  5. fail-open 認證（A10 / CWE-636）。寫一個權限檢查函式，讓它在「資料來源故障」時回傳 True，然後觀察未授權者如何因此放行。修補成 fail closed（例外時拒絕並回 503）。這個練習比 SQLi 更能訓練邏輯漏洞思維：漏洞不在語法，而在「例外處理的方向錯了」。
  6. 依賴掃描（A03）。用 pip-audit 或 OSV API 掃描自己專案的依賴，找出版本落後且已有 CVE 的套件。體會「自己的專案也是供應鏈的一環」——你沒直接引入的套件，也可能透過間接依賴進入。
  7. 日誌與警報（A09）。設計一個登入端點，先刻意不寫任何日誌，然後連續失敗 10 次——觀察「攻擊者有進度資訊，防禦方零資訊」的反諷。接著修補成 結構化 JSON 日誌 + 告警門檻 + 敏感欄位遮罩 + request_id 貫穿。驗證時注意：A09 的漏洞不在回應裡，而在日誌與告警檔案中——這是它與注入類漏洞在驗證方式上的根本差異。
  8. 加密與設計缺陷（A04 / A06）。做一個電商情境：先實作 check-then-act 的扣款邏輯，用併發請求把餘額扣成負數；再實作「客戶端提供價格」的信任邊界錯誤。修補時體會 A06 的核心——設計缺陷無法靠實作修補：要把檢查條件放進動作本身（單一原子 UPDATE ... WHERE balance >= ?），而不是「先檢查再動作」。密碼儲存改用 PBKDF2/Argon2 並加 salt，隨機 token 改用 secrets。
  9. 安全設定排查（A02）。拿一份現成的 HTTP 服務，用下列清單逐項檢查：回應標頭（CSP、X-Content-Type-Options、HSTS 等 6 項）、允許的 HTTP 方法（送 PUT/DELETE 看是否被拒）、預設憑證（admin/admin 等常見組合）、偵錯端點（/env、/debug、/actuator）、錯誤訊息（是否洩漏 traceback 或區分帳號存在性）。重點體會：A02 的漏洞不在 body，而在標頭與伺服器行為——這是第五種驗證型態。同時注意這類檢查幾乎完全可自動化，不需要 LLM。
  10. 供應鏈深度：依賴樹、非對稱簽章與 CI（A03）。（1）間接依賴樹：用 pip-audit 或自製工具展開整棵依賴樹——體會「你的 requirements.txt 只有 8 行，但實際依賴樹有 17 個節點」，而 Log4Shell 正是從沒被直接引入的那一層進來的。（2）非對稱簽章：比較 HMAC 與 RSA/Ed25519 的差異——HMAC 的驗證者持有密鑰所以也能偽造，無法證明「來源」；非對稱簽章用公鑰驗證，才能真正建立信任鏈（根 CA → 發佈者憑證 → 產物簽章）。（3）CI 整合：把上述檢查寫進 CI（含每週排程重掃，因為「今天安全」不代表「明天安全」），並把相依性檔案的變更視為需要人工審查的事件。
  11. 真實案例實測：CVE-2020-1747（PyYAML 反序列化 RCE，CVSS CRITICAL）——從本專案掃描出的 166 個漏洞中挑選一個，實際下載官方原始碼並在本地複現。測試 4 個版本（5.1／5.2／5.3／5.3.1）× 多種攻擊向量，載荷僅為無害的 echo。結果：python/object/new 在 5.2／5.3 可執行任意程式碼；5.3.1 新增的 state 鍵黑名單（['^extend$', '^__.*__$']）成功攔下 __reduce__——錯誤訊息為 blacklisted key '__reduce__' in instance state found，是修補生效的直接證據。而 safe_load() 從頭到尾都正確攔阻。
    三個關鍵教學點：（1）問題不是函式庫有缺陷，而是開發者選錯了 API——同一個套件，safe_load 安全、full_load 危險；（2）CVE 的「修復版本」欄位要理解為「這個具體向量被修補」，不是「這個 API 從此安全」（實測 5.3.1 仍可用 object/new 建立行程物件）；（3）下載舊套件複現要注意舊版 PyYAML 有 lib/（Python 2）與 lib3/（Python 3）兩份原始碼，用錯目錄會全部匯入失敗。

第二階段：工具鏈 建議 2–3 個月｜目標：能為一個真實開源專案建立可重複的漏洞發現流程

這一階段的產出標準是：對一個 OSS-Fuzz 收錄的專案，在本機成功建置、跑起 fuzzer、並重現至少一個既有 crash。

必學主題

  • Fuzzer 原理與實作：coverage-guided fuzzing 的基本迴圈（seed → mutate → execute → 收集 coverage → 保留有價值輸入）、AFL 的 forkserver 與 shared memory coverage、libFuzzer 的 in-process 模式、corpus 最小化（afl-cmin、afl-tmin）。
  • Fuzz harness 撰寫：這是 AI 進入此領域後最有價值的技能。學會為一個 library 寫出「不吃 stdin、直接呼叫 API、正確處理記憶體釋放」的 harness，並用 LLVMFuzzerTestOneInput 介面。
  • Sanitizer：ASan（記憶體錯誤）、UBSan（未定義行為）、MSan（未初始化讀取）、TSan（資料競爭）。理解 ASAN_OPTIONS、UBSAN_OPTIONS 的關鍵開關，以及 sanitizer 報告中的 SUMMARY 行如何對應到 bug 類型。
  • 除錯與觀測：GDB 的 breakpoint / watchpoint / bt / x 指令；用 rr 做可重播的除錯；用 crash 的 stack trace 回溯到根因。
  • 靜態分析：CodeQL 的查詢語言基礎（from ... where ... select）、資料流庫（DataFlow::Configuration）；Semgrep 的 pattern 語法與 --config auto。重點是理解「規則如何表達資料流」，而不是背 API。
  • 建置系統：CMake、Makefile、以及 OSS-Fuzz 的 build.sh 慣例。很多時候真正的困難是「讓它編起來」。

可執行練習

  1. 自製目標 + AFL++ 完整迴圈。寫一個刻意有漏洞的 C 程式（讀取檔案格式），用 afl-cc 插樁編譯，準備 3 個 seed，跑 30 分鐘，觀察 afl-whatsup、coverage 成長與 crash 出現。然後用 afl-tmin 最小化 crash 輸入。
  2. libFuzzer 重寫同一題。改用 LLVMFuzzerTestOneInput + -fsanitize=fuzzer,address，比較與 AFL++ 的差異（速度、發現時間、corpus 品質）。寫下你的觀察。
  3. 重現一個真實 OSS-Fuzz crash。挑一個 OSS-Fuzz 收錄的專案，依其 Dockerfile／build.sh 在本機建置，用 reproduce 腳本重現一個已修正的 crash。這一步會讓你理解「容器化重現環境」為什麼是 CyberGym 等 benchmark 的基礎設施。
  4. 寫一條 CodeQL 規則。對一個小型 C repo 寫一條找出「未檢查回傳值的 malloc」或「格式字串來自外部輸入」的查詢，記錄命中數與誤報數。然後改寫成 Semgrep 規則，比較兩者的表達力與誤報率。
  5. GDB 根因分析。拿練習 1 的 crash，用 GDB 找出確切的指令與變數值，寫一份一頁的 RCA：崩潰點、傳入值、為什麼會超過邊界、正確的修法。這份 RCA 就是未來餵給 LLM 做變體分析的完美起點。
  6. 跑一次完整的 CRS（進階）。在 Linux 環境上依 Buttercup 官方說明以 standalone 版本跑官方內建的易受攻擊 sample repo（官方稱可在 10 分鐘內找到並修補）。重點不是「找到漏洞」，而是觀察一個競賽級系統如何把 fuzzer、sanitizer、靜態分析與 patch 驗證串成自動迴圈，並閱讀它「PoV 不再觸發 + 其他功能不破壞」的雙重驗證條件。

第三階段：AI 方法 建議 2–3 個月｜目標：能設計並量測一個 AI 漏洞挖掘 agent

這一階段的產出標準是：在一個公開 benchmark（如 CyberGym 的子集）上，跑出可重現的成功率數字，並能解釋失敗案例的原因。

必學主題

  • Prompt 設計（針對漏洞研究）：不是「請找漏洞」，而是明確指定任務型態（variant analysis vs 開放式探索）、可用的工具、輸出格式（必須附可執行的 testcase）、以及不確定時的處理方式（要求標示不確定，而非編造）。Big Sleep 的 prompt 設計關鍵是：給 agent「commit message + diff」，並請它審查當前 HEAD 的相關問題——把開放問題轉成有先驗的問題。
  • Agent 架構：工具定義（schema）、狀態管理、失敗恢復策略、context 壓縮、多輪預算控制。研究並比較三種架構（單 agent 長 context / 多 agent 分工 / 大量短生命週期 agent + coordinator）在成本與成功率的差異。
  • 工具整合：讓 agent 能呼叫 code browser、編譯器、debugger、fuzzer、sanitizer。核心設計原則：所有產出必須可被外部機制證偽。
  • 評估指標：這是本階段最重要的知識點。必須能區分並正確計算：
指標定義常見誤用
Pass@1（單次成功率）一次嘗試就成功的任務比例與 Pass@k 混用而誇大能力
Pass@k / best-of-kk 次嘗試中至少一次成功的比例不提成本就宣稱進步（CyberGym 從單次約 30% 到 30 次約 67%）
False positive rate報告為漏洞但無法觸發的比例完全不報，只報成功率
Recall（針對已知漏洞）給定描述後能重現的比例與「開放式發現」混為一談
Novel discovery rate在無已知答案下找到新 bug 的比例Anthropic 數據：單次約 5%，30 次超過 33%
Cost per verified bug每個經人工確認的漏洞的總成本只算 API 費用，忽略 triage 工時
Trajectory efficiency工具呼叫次數、無效步驟比例、token 用量忽略「花了 200 步才找到」的可持續性問題

可執行練習

  1. 建立變體分析迴圈。挑一個自己熟悉的開源專案，找一個已修補的安全 commit。寫一個腳本：把 commit message + diff 交給 LLM，要求它在當前版本找同類問題，並產出 testcase；然後自動編譯執行、檢查是否崩潰。量測：產出多少假設、多少能編譯、多少真的崩潰。
  2. 對照三種 prompt 策略。同一題、同一個模型，比較（a）純問答式、（b）要求輸出 testcase、（c）agent 可用工具並可迭代。用「能否產出可觸發的 PoC」為唯一判準，記錄成功率與 token 成本。
  3. 接上 sanitizer 當裁判。把你的 agent 輸出強制經過「編譯 + 執行 + sanitizer 檢查」三道關卡，並統計被這三道關卡擋下的比例。這個比例就是你對 LLM 幻覺的實際量測。
  4. 跑 CyberGym 子集。以官方提供的容器化環境跑 20–30 個任務，計算 Pass@1 與 Pass@10，和公開 leaderboard 的數字對照，分析你的失敗案例屬於哪一類（檢索失敗／假設錯誤／環境問題／模型能力不足）。
  5. Harness 生成實驗。用 oss-fuzz-gen 或自建流程，為 5 個 OSS-Fuzz 專案生成 fuzz target，量測：build 成功率、是否提升 coverage、是否觸發 crash。這是把 LLM 用在可自動驗證環節的最佳練習。
  6. 實作「偽造定義」偵測（借鏡 HarnessAgent 研究）。該研究發現 LLM 會偽造不存在的函式定義來讓 harness 通過編譯（研究中 56 個 harness 有 10 個以上含此類偽造）。請在你的生成流程加入結構化檢查：解析生成的 harness，確認呼叫的每個函式都真的存在於專案符號表中。沒有這道檢查，「能編譯」就是一個無效的成功判準。
  7. 讀一篇訓練配方論文並複現其評估設定。精讀 VulnLLM-R，重點看它如何用雙教師蒸餾 + 錯誤答案過濾 + constitution-based correction訓練 7B 模型，以及它公開的失敗經驗（以 GRPO 做線上 RL 導致 false negative rate 大幅上升的 reward hacking 現象）。這是理解「AI 方法成敗取決於資料與獎勵設計」的最佳教材。
  8. 把狀態寫出 context（journal 模式）。照 IronCurtain 的設計做一個最小實驗：讓 orchestrator 不直接讀原始碼，只依賴一份 append-only 的執行日誌（記錄假設、做過的工具呼叫、觀察結果）來決定下一步。比較「全放在 context 裡」與「狀態外置」兩種做法，在同一任務上執行到第 20、40、60 步時的準確率與 token 用量。這是理解「為什麼長流程 agent 會失準」最直接的方式。
  9. 成本量測（把 cost per investigation 變成你的指標）。記錄單次完整調查的 token 數與費用，與公開基準對照：IronCurtain 報告 Opus 約 150 美元／1,000 萬 tokens、Sonnet 約 30 美元；CyberGym 的成本上限是每漏洞 2 美元。思考兩者的差異來源——「已知漏洞重現」與「開放式調查」是不同量級的任務，若把兩者的成本混為一談，預算估算會嚴重失準。
  10. 多 agent 分工實驗（HPTSA 模式）。依 EACL 2026 的 HPTSA 設計，實作一個「規劃 agent + 可被呼叫的 subagent」架構：規劃 agent 只負責探索與決定呼叫哪個 subagent，不親自解題。與單一 agent 比較成功率（該論文在 14 個真實漏洞上報告最高 4.3 倍提升），並記錄 subagent 之間的成功案例重疊度。
  11. Crash triage 實驗。收集 20 個 crash（可用 fuzzer 自產），要 LLM 判斷是否同源並分類 CWE，與你的人工判斷比對，計算準確率與一致性。

7.1 如何選擇與正確解讀

  • 想提升「重現能力」→ CyberGym。它有客觀的自動判分（sanitizer 執行），且有 188 個專案的多樣性。
  • 想提升「長流程工具使用」→ Cybench。多階段任務會暴露 agent 在狀態管理上的弱點。
  • 想提升「修補品質」→ AIxCC 架構 + CyberGym 的 patch 研究設定。注意 Anthropic 已指出「與參考 patch 比對」的方法會產生 false negative（同一漏洞常有多種合法修法），因此不要用單一比對法當唯一判準。
  • 想提升「實際 fuzzing 產出」→ OSS-Fuzz。這是最接近產業實務的場域，且貢獻成果可被維護者驗證。
解讀 benchmark 數字的三個檢查點 （1）是 Pass@1 還是 Pass@k？CyberGym 的單次約 30% 與 30 次約 67% 相差一倍以上。 （2）成本限制是否一致？Anthropic 明確說明 Opus 4.1 因價格較高未套用相同的 2 美元限制，因此其單次數字不可與其他模型直接比較。 （3）任務是否給了提示？給定「位置、類型、root cause」的重現任務，與無提示的開放式發現，是兩種不同的能力。

CH 08合法與倫理邊界 Legal & Ethical Boundaries

本報告的撰寫視角 本報告以教育與防禦研究為目的，僅涵蓋公開資料、公開競賽、開源工具與研究方法。報告中不包含任何針對特定真實目標的攻擊步驟、可直接利用的 exploit 程式碼或繞過防禦的操作流程。所有涉及漏洞發現的練習，都必須在自身擁有或已取得明確書面授權的環境中進行。

8.1 授權測試：法律風險的第一道線

  • 「未授權存取」在多數司法管轄區都是刑事犯罪。在台灣，《刑法》第 358 條至第 363 條針對無故入侵他人電腦、取得電磁紀錄、干擾系統等行為設有刑責；美國則有 CFAA（Computer Fraud and Abuse Act）。「我只是研究」不是抗辯理由。
  • 書面授權必須明確。一份可用的授權應載明：測試目標的具體範圍（域名/IP/服務）、時間窗口、允許的技術（是否允許 DoS、社交工程、資料外洩測試）、聯絡窗口、以及緊急停止機制。
  • Safe harbor 條款：部分平台與組織提供 safe harbor，承諾對善意遵循其政策的研究者不提告。動手前務必確認目標是否有此條款，以及其適用條件。
  • 第三方服務是常見陷阱。目標網站可能使用第三方 CDN、雲端服務或 SaaS——這些通常不在授權範圍內，即使它們是目標架構的一部分。
  • 自動化工具的放大風險。AI agent 會以極高頻率發出請求，可能導致服務中斷、大量日誌、或觸發第三方服務的濫用偵測。在授權範圍內部署自動化工具時，必須設定速率限制與範圍約束（XBOW 的公開說明即強調 scope control 在網路層強制執行、每個 agent 只在有限序列內行動）。

8.2 Bug Bounty 與負責任揭露流程

典型流程（防禦方視角）

1. 選擇目標與閱讀政策    確認 scope、safe harbor、禁測項目、獎金規則
        │
2. 發現疑似的安全問題    最小化驗證，取得「剛好足夠」的證據
        │
3. 自驗證與最小化        確認可重現、排除環境因素、去除破壞性步驟
        │
4. 撰寫報告              影響評估 + 重現步驟 + 修補建議（見下）
        │
5. 通報（Disclosure）    透過平台或專案的安全聯絡管道
        │
6. 協調等待期            通常 90 天為業界常見慣例，可依情況協商
        │
7. 修補驗證與公開        確認修補生效後，才考慮公開技術細節

一份好的漏洞報告應包含

  • 摘要：一句話說明問題與影響。
  • 影響評估：誰受影響、什麼條件下可被觸發、可能的後果（不提武器化細節）。
  • 重現步驟：最小、可重複、非破壞性。避免包含「如何擴大影響」的完整鏈路。
  • 證據：日誌、截圖、最小 PoC 輸入（僅足以觸發，不具武器化價值）。
  • 修補建議：具體可行的方向（例如「在進入 sink 前對長度做上限檢查」）。
AI 輔助揭露的特別注意事項 用 AI 掃描 bug bounty 目標時，不要提交未經自己驗證的 AI 輸出。理由有三：（1）誤報會浪費 triager 時間，可能導致帳號信譽受損；（2）若平台政策禁止自動化掃描，可能違反規則；（3）AI 產出的 PoC 可能包含你不理解的副作用。AI 負責廣度，人負責驗證與判斷。

8.4 研究倫理：AI 時代的額外考量

  • 雙用途（dual-use）意識。Anthropic 公開說明其在提升 Claude 防禦能力的同時，刻意避免強化明確偏攻擊的能力（如進階利用或撰寫惡意程式）；AIxCC 亦要求所有 CRS 技術開源。這類「能力提升與風險控制並行」的設計思維，值得研究者參考。
  • 評測揭露的責任。若你的研究顯示某個模型能大量發現真實漏洞，公開時應考慮：是否同時揭露緩解措施、是否已走完負責任揭露、是否提供防禦方可用的資訊。
  • 避免「AI 洗版」。大規模自動化通報低品質 finding，會污染整個生態系的 triage 資源（包括開源維護者的志工時間）。這不是假設性風險，而是已經發生的事實：curl 專案因其 bug bounty 計畫被 AI 撰寫的提交淹沒而關閉該計畫（多為未經確認的 finding）；FFmpeg 維護者批評 Google 提交有效 bug 卻未附修補，稱之為「CVE slop」。實務原則：沒有附帶驗證與可套用修補的自動化通報，不應送出。
  • Anthropic 的雙軌策略值得參考。Anthropic 一邊公開其模型能找到 500+ 個高嚴重性漏洞，一邊隨模型發布以 probes（量測生成時之內部活化值）為核心的濫用偵測層，並可能採取即時干預（含阻擋惡意流量）。他們同時誠實承認這會對合法研究與部分防禦工作造成摩擦。這種「能力提升與風險控制並行、並公開承認副作用」的作法，是研究者撰寫相關論文或發布工具時可以模仿的揭露姿態。
  • 把「修補」納入流程，否則成本會外部化。上述兩個案例的共同點是「AI 自動化停在發現就結束」。AIxCC 的 CRS 設計明確要求以 PoV 確認漏洞並產生通過驗證的 patch——這是自動化應該追求的完整鏈路，也是避免把成本外部化給維護者的關鍵設計。
  • 記錄與可審計性。AI agent 的每一步決策都應留下可審計的 trajectory，以便事後解釋「為什麼發出這個請求」。這既是技術需求，也是合規需求。
  • 揭露時程的判斷。90 天是常見慣例但非硬性規定；若涉及仍在野利用（in-the-wild exploitation）或關鍵基礎設施，應與廠商協調更短或更長的窗口。AI 時代的新問題：Anthropic 在 2026-02 的研究中明確指出，業界標準的 90 天窗口「可能無法承受 LLM 發現漏洞的速度與數量」，業界需要能跟上節奏的新工作流。當單一組織能在數月內產出 500 個以上高嚴重性漏洞時，逐一手工協調揭露與修補的流程會成為瓶頸——這是目前尚未有共識解的政策空白。
  • 誤報是揭露流程的隱形成本。Anthropic 在其大規模研究中特別說明，幻覺（hallucinated bugs）「正日益對開源開發者造成不當負擔」，因此他們在通報每個漏洞前都做了大量驗證，並以降低誤報為流程的最佳化目標。這與 curl、FFmpeg 的案例（CH03）指向同一個結論：負責任的自動化必須把驗證成本留在自己身上，而不是轉嫁給維護者。
